# The builder as an authoring surface, not a runtime

## Why this shape is different in kind

Both shapes round one considered move the model call. Shape (a) imports the builder as a library and runs the graph in this process; shape (b) runs the builder as a service and streams tokens back over a socket. Either way the builder becomes the thing that talks to the model, which is why every candidate was scored on whether it can emit token deltas.

This third shape moves nothing. The TypeScript agent keeps calling the model, keeps holding the ConversationRelay WebSocket, keeps dispatching tools. The builder becomes the place a human edits the system prompt and picks which tools this version of the agent may use, and then publishes that as configuration the runtime fetches. Streaming stops being a requirement of the builder, because the builder is never in the request path of a turn.

The strongest argument for taking it seriously is that this scaffold already works this way, with Langfuse as the authoring surface. Reading the scaffold source, the prompt seam validates a free-form JSON blob edited in a web form against a strict schema, and that blob carries the model id, the tool-choice mode, a step ceiling, and the list of enabled tools alongside the prompt text (symbols `PromptConfigSchema` and `ResolvedPrompt`, read from the scaffold source). The comment on that schema states the design in one line: changing the tool selection is a new prompt version plus a label move, with no redeploy and no container restart, and rollback is moving the label back. So the question this page should ask is not whether the shape is achievable. It is whether any of the surveyed builders is a better authoring surface than the prompt manager already in the stack.

## 1. What the shape actually requires of a builder

Four things, and nothing else.

First, it must export prompt text in a form a program can read without a browser, either over an HTTP API or as a file a repository can hold. Second, it must export the tool selection as a list of names, not as schemas, because the schemas belong to the runtime that executes them. Third, every published state needs a stable identifier, so that a trace recorded three weeks ago can name the exact prompt that produced it. Fourth, it needs a publish or activate operation distinct from saving, so an operator can edit without the edit reaching live callers, and can move production back to a previous state without a deploy.

Nothing in that list mentions streaming, deltas, abort signals, or transports. Requirement 2 from round one, token-level streaming out of the runtime, stops applying to the builder entirely, because the runtime that streams is the one already in this process. In this scaffold that streaming path is `VoiceChannel.sendStreamingResponse`, a public method that consumes an `AsyncIterable<string>` and does one synchronous `ws.send` per chunk (read from the shipped `twilio-agent-connect` bundle). Under this shape that code does not change at all.

Two implicit requirements are worth naming because they are where the surveyed builders are weakest. The exported prompt must be addressable as a prompt, not only as a field buried in a graph document, or the runtime has to parse a graph format that no vendor documents as an interface. And the exported tool list must survive the round trip in the order the author put it, because that order is part of the byte sequence sent to the model on every turn.

## 2. Which surveyed candidates can serve as an authoring surface

This reopens candidates that round one eliminated purely on streaming grounds. Julep was failed because its own FAQ says streaming is planned and not implemented. Kestra was failed because its execution model produces task outputs rather than token deltas. CrewAI Studio was failed for being a Streamlit app. Dify's newer agent node was failed for emitting delta counts instead of delta text. Flowise's streaming was found to degrade silently unless the agent node is last in the flow. None of that matters in this shape. A builder that cannot stream a token is a perfectly good place to write a prompt.

The same move promotes a whole category the sweep dismissed. Agenta, Opik, Lunary and Latitude were all set aside as prompt management and observability tools with no orchestration runtime, which is exactly the disqualifier that turns into a match here. Langfuse, which the round-one recommendation kept only for tracing, is already the incumbent in that category and already satisfies all four requirements above, including the label indirection that makes rollback a pointer move rather than a republish.

Judged on export and versioning rather than on streaming, the six round-one candidates fall out roughly like this.

Langflow is the best fit among them. A `flow_version` table holds a full JSON snapshot per version with a monotonic `version_number` unique per flow and a computed `v{n}` tag, and the MIT tree exposes list, fetch, create, delete and a real `POST /{version_id}/activate`, which is rollback without a container restart ([repository](https://github.com/langflow-ai/langflow), [LICENSE](https://github.com/langflow-ai/langflow/blob/main/LICENSE)). Two costs. The versioning router is registered with `include_in_schema=False` and appears nowhere in the published docs, so it is an internal API that may change without a note. And the prompt is a field inside the flow JSON rather than a first-class object, so extracting prompt text and tool selection means parsing a graph schema that is not a documented interface, and diffing two versions means diffing two whole graphs.

Dify offers the same shape one notch coarser. Workflow rows carry a version string plus a user-facing monotonic number, published versions are listable, and a restore-to-draft endpoint gives rollback ([repository](https://github.com/langgenius/dify)). The license is the blocker rather than the mechanism: it is Apache 2.0 with two added conditions, GitHub reports NOASSERTION, and it forbids operating a multi-tenant environment without written authorization ([LICENSE](https://raw.githubusercontent.com/langgenius/dify/main/LICENSE)). Since this shape needs only the authoring half of Dify, adopting a non-OSI license and a large container footprint to obtain a prompt editor is a poor trade.

LangGraph is interesting in this shape for a reason unrelated to its graph library. Its assistants abstraction is a graph plus a configuration, and the MIT JavaScript server implements per-assistant version listing plus a set-latest call for rollback ([langgraphjs](https://github.com/langchain-ai/langgraphjs)). That is a genuine publish-and-roll-back surface for prompt and tool availability. The catch is that assistants are a server-side concept, so adopting the versioning means running the server tier, and its own documentation warns that updating an assistant requires sending all configuration fields, so a partial update silently drops values. The visual surface also pulls in a hosted dependency this stack does not currently have.

Flowise fails the version requirement outright. Its chat-flow entity has no version column and no history table anywhere in its entity list, and saving a flow overwrites the flow data in place ([repository](https://github.com/FlowiseAI/Flowise)). Exported flow JSON committed to a repository would supply the missing identifier, but then the version record lives in git and the builder is only an editor, which is a defensible arrangement and not one Flowise gives you.

Rivet inverts that trade in a way that suits this shape well. The project file is YAML holding the prompt text inline, so a commit hash is the version identifier, review is a pull request, and rollback is a revert ([repository](https://github.com/Ironclad/rivet)). There is no activate operation and no label, and the desktop editor is the authoring surface rather than a web console. The decisive problem is upkeep: round one found no feature release in roughly fifteen months and dependency-bump commits only.

Letta is the one to decline. Its system prompt is composed from memory blocks held in a real git repository per agent, with a content hash and a revision recorded per compiled prompt, which is excellent provenance. But the agent rewrites those blocks itself, so the prompt is a moving target committed by the agent rather than approved by a human, which is the opposite of the approved-version-per-release model this shape exists to provide ([repository](https://github.com/letta-ai/letta-code)).

One consequence for the round-one winners deserves stating plainly. Coze Studio was ranked strongest overall partly on its streaming protocol, and in this shape that advantage evaporates while its stated absence of any flow export or import, with in-workspace copy only, becomes a hard failure of requirement one of the four above. Sim and Windmill both remain plausible on their versioned deployments and their resource model respectively, and both need the same export-and-identifier check the six above just received. Windmill's agent resource in particular resolves live rather than being pinned to a run, which is the same live-edit hazard the current arrangement has and not an improvement on it.

## 3. The honest cost

Requirement 3 is not met. The requester marked it hard, and this shape does not satisfy it. Tool implementations stay in the TypeScript source. A non-engineer can rename a tool's description, reorder the selection, remove a tool from a version, and roll the whole thing back, but cannot create a capability that did not previously exist in the repository. Anyone who tells you otherwise is counting a builder's tool-registration screen as an implementation, and round one's adversarial pass already caught that error once: of the four mechanisms claimed for Dify, only the code node authors an implementation in the console, while the HTTP-tool and remote-tool paths are definition-only and require the implementation to be written and hosted in your own source anyway ([corrected verdict, Dify record](https://github.com/langgenius/dify)).

What relaxing that requirement buys is unusually concrete here, because every item on the list is a thing that has been measured or read rather than assumed.

The trace survives whole. Every `gen_ai.*` attribute on this scaffold's generation spans is produced by the AI SDK inside this process, including `gen_ai.client.operation.time_to_first_chunk`, which is the one instrument that answers "is this us or is it the model" in a single query. Move the model runtime out and that instrument leaves with it. In this shape it does not move, so the tiled voice timeline, the per-turn generation spans, and the prompt-version link on the generation all keep working unchanged.

The framework cost stays where it was measured, which is small. The preamble before the model stream starts was attributed at a ceiling of 84 ms on the worst single turn out of 33 generations captured on one day with one caller and one model, with a range of 0 to 84 ms across turns; that is a ceiling and not a mean, and it is not a benchmark. Everything else in a turn is model time. Adding a network hop to a builder puts a new term into that budget, and this shape adds none.

The provider prompt cache keeps working, which is the largest number on the page. On one measured call the first turn's first generation took 3838 ms to first chunk against a cold cache on a two-generation tool-calling turn, while the following turns on the same call reported cached input tokens and ran 0.51 to 0.71 s; those warm figures are turn two onward on a single call and mean nothing quoted without that qualifier. The difference between those two states is whether the system prompt prefix is byte-identical to the previous turn. A builder that recomposes the prompt per run, reorders tool definitions, or injects a run identifier into the prefix converts every turn into a cold turn. Keeping composition in this process keeps that under our control, and the scaffold's resolver already preserves the prompt's tool order and collapses duplicates to their first occurrence rather than re-sorting (symbol `resolve`, read from the scaffold source).

The abort path stays intact. On barge-in the interrupt frame aborts the stream task, and the scaffold passes its own signal into the streaming call because the library resolves the signal as the caller's option first and its own active task second (read from the shipped bundle). Nothing about that changes, and no abort has to be forwarded across a network boundary to a second runtime.

The platform tools stay native. The shipped bundle exports `defineTool`, the `TACTool` class, and factory helpers `createMemoryRetrievalTool`, `createMemoryTools`, `createSendMessageTool`, `createMessagingTools`, `createStudioHandoffTool`, `createKnowledgeSearchTool`, `createKnowledgeSearchToolAsync` and `createKnowledgeTools`, plus a `BuiltInTools` map whose values are the four canonical names `retrieve_profile_memory`, `send_message`, `handoff` and `search_knowledge` (read from the shipped bundle). Under this shape those remain what they are. Under either runtime-moving shape each one becomes a shim you write and maintain.

The repository's own guard tests survive. The enforced import boundaries that keep the agent core channel-agnostic, and the tripwire tests that assert those rule sets are intact, are written against a runtime that lives here. Moving the runtime deletes or inverts them, and that cost belongs in the estimate for the other two shapes.

And the requester gets what they described wanting, which was a visual way to manage prompts and add tools, not a new runtime.

## 4. Versioning tool selection alongside the prompt

The obvious failure is a prompt that instructs the model to use a tool the runtime does not have. The scaffold's answer is worth stating as the general recipe, because it is already load-bearing here.

A version record must carry the prompt name; an integer version; the label the runtime fetches by, since fetching by label is what makes rollback a pointer move; the prompt messages with named placeholders left unexpanded; the tool selection as an ordered list of names and never as schemas; the model identifier; the tool-choice mode; and a ceiling on agent steps. Two optional model parameters round it out. In this scaffold that is exactly the strict schema the prompt port validates, and the comment above the tools field states the reason names are the only permitted form: schemas live in a code-owned catalog, so an edit in the authoring surface selects from an allowlist and structurally cannot add a new tool or alter an existing tool's arguments (symbol `PromptConfigSchema`, read from the scaffold source).

Strictness matters more than it looks. Validation rejects unknown keys rather than stripping them, because a free-form JSON form invites `max_steps` where the schema says `maxSteps`, and the stripping behaviour would serve a default while the operator believed they had set something else, with nothing anywhere reporting the difference. A rejected config falls back to the compiled default with a named warning, which is loud.

Validation before serving a turn happens in two places with deliberately opposite failure modes. At boot, the compiled-in defaults are preflighted and a name nothing answers to is a startup error, because those defaults are code and a bug in them can be shouted about before any call arrives. At runtime, resolution never throws: the requested names are partitioned into resolved, unknown, and unavailable, the turn proceeds with whatever resolved, and the caller decides nothing. Unknown means the name is absent from the catalog, which is a typo or a removed tool, and it warns. Unavailable means the catalog has the tool but this process lacks the capability it requires, which is the ordinary state of a half-configured environment, so it logs at debug (symbols `resolve` and `ToolDef.requires`, read from the scaffold source). A prompt version naming a dead tool must not be able to take a live phone call down.

The last piece is attribution. The turn span records the prompt name, version and label, the offered tool list, and the unknown list, so a bad selection is attributable to the version that caused it rather than to the call that suffered it. One honest limit applies to how that is read: a top-level prompt link set on a span that is not a generation does not resolve into a prompt reference in this trace store's ingestion, because the link is computed only for generation observations, so attribution is read off the sibling generation span instead. Verification of that used the datastore directly, because the self-hosted trace store here exposes no public read API for traces and a 404 from it means disabled rather than empty.

There is one more reason to keep the tool list ordered and deduplicated that has nothing to do with correctness. Tool definitions were measured at 4035 characters for five tools on one generation, roughly a third of that generation's system prompt when the parts are compared as character shares. Those shares are reliable; the absolute token counts derived from them are not, because dividing characters by four overestimated the tokenizer's own count by about 24 percent on that same generation. Since every character of that block is sent on every turn and the prefix must stay byte-stable for the cache to hold, the version record is also the thing that pins the prompt's cache identity.

## 5. Is the hybrid coherent

Yes, and it is the only way this shape gets anywhere near requirement 3. The builder authors prompt and tool selection as above, and also implements business tools that it executes itself, which the runtime reaches by making an HTTP call from inside a tool implementation. The platform tools stay native, because they are already `TACTool` objects wrapping Twilio clients and there is nothing to gain by proxying them.

The mechanism is available without any work on the library's side. The shipped bundle never invokes a tool at all: `TACTool.implementation` is read in only two places, the constructor and the adapter that converts a tool for one external agent SDK, while the OpenAI and Anthropic conversions emit schema only, so tool dispatch belongs entirely to the model runtime in this process (read from the shipped bundle). A generic outbound tool whose URL, name, description and argument schema come from the version record is therefore a small addition to the catalog rather than a change of architecture.

The trace consequence is specific, and it is the thing to draw. When a tool call leaves the process you do not get a second trace tree, which is what happens when the model runtime moves. You get one tree with a hole in the middle of a turn: the tool span still exists as a child of the model step, still carries a real duration, and still shows the arguments the model chose, but it has no children, so the time inside it is unattributed. That is a much better failure than two disconnected trees, and it is still a regression from today, where a tool's interior is either trivially fast or explained by a known network dependency. For scale, one measured turn had a tool that returned in about 1 ms and another that took 417 to 1018 ms across a small single-day sample because it queries a real knowledge base over the network. An opaque span in the second range is the shape to expect, and it lands in the middle of a turn a caller is waiting through. Closing the hole means the builder must accept a W3C `traceparent` on the tool call and continue the trace, and whether any surveyed builder does that is unknown and was not checked in either round.

Two further costs, both concrete. There is no abort path into a business tool today: the tool context passed to an implementation carries a conversation id, a logger and a profile id, and no abort signal (symbol `ToolCtx`, read from the scaffold source). So on barge-in the model stream stops but an in-flight outbound tool call keeps running until it completes or times out, and threading a signal through is prerequisite work rather than a detail. And a tool that runs in the builder runs wherever the builder runs, with whatever code-execution surface that builder exposes to whoever can log into it, which is a security decision to make deliberately and in the open rather than in a footnote.

## 6. Recommendation

Make this shape the spine of the page, and demote the other two into a section about what moving the runtime costs.

Three reasons. It is what was asked for, which was a visual way to manage prompts and add tools rather than a replacement runtime. It is the only one of the three shapes where the hardest requirement of round one, token-level streaming out of the builder, simply does not apply, which changes the candidate set enough that the round-one ranking should not be published as-is. And it is the only shape with a working reference implementation to point at, because the scaffold already publishes prompt text and tool selection from an authoring surface, fetches by label, validates strictly, resolves names against a code-owned catalog, and records the resulting selection on the turn span. A page that leads with this can show a mechanism instead of proposing one.

The page must then be blunt in the same breath: this does not satisfy the requirement that tool implementations be authored outside our source, and the hybrid buys that back only for business tools and only at the price of an unattributed span inside the turn plus an abort gap. If the requirement is truly immovable, the honest answer is that no surveyed candidate satisfies it without moving the model runtime, and moving the model runtime costs the per-generation instrument the rest of the analysis depends on.

The remaining engineering question worth a spike is small and cheap, which is itself an argument for the shape. Take one candidate that has a documented publish-and-activate operation, read a prompt and a tool-name list out of its export, serve three turns from it, and check two things: that the composed system prefix is byte-identical across turns so the cache still hits, and that a version naming a nonexistent tool degrades to a warning rather than a dropped call. Neither check requires the builder to stream anything.

## Unverified

- Whether any surveyed builder accepts a W3C traceparent on an inbound tool-execution call and continues the trace. Not checked in either round; this decides whether the hybrid's mid-turn span is opaque or explained.
- Whether Langflow's version-activate route stays stable. It is present in the MIT tree with a real POST /{version_id}/activate, but it is registered with include_in_schema=False and appears in no published doc, so it is an internal API by the maintainers' own signalling.
- Whether prompt text and tool selection can be extracted from any surveyed builder's export without parsing an undocumented graph schema. In all six round-one candidates the prompt is a field inside a flow document rather than an addressable object, and no vendor documents that document as an interface.
- Whether any surveyed builder produces a byte-stable system-prompt prefix across turns. The prompt-cache argument is reasoned from how prefix caching works plus this scaffold's own measured cold-versus-warm gap on a single call, not from an experiment against any candidate.
- Whether Sim and Windmill satisfy the four authoring-surface requirements. Both were ranked in round one partly on streaming, which no longer applies; their export format, version identifier and publish operation were not examined under these criteria. Windmill's agent resource is documented as resolving live rather than being pinned to a run, which is a hazard rather than an improvement.
- Coze Studio's stated absence of any flow export or import (in-workspace copy only) is taken from the round-one record and was not re-verified. It is the fact that eliminates the round-one favourite under this shape's criteria, so it should be rechecked before publication.
- The abort gap in the hybrid rests on reading the scaffold's tool context type, which carries no abort signal. Nobody has run a barge-in during an in-flight outbound tool call to observe what the orphaned request does.
- All latency figures quoted come from a single day, one caller, one model, and small samples: the 84 ms preamble ceiling from the worst of 33 generations, the 3838 ms cold first chunk from one cold-cache two-generation turn, the 0.51 to 0.71 s warm turns from the following turns of that same call, and the 417 to 1018 ms tool from a handful of calls. None is a benchmark and none should be quoted without its qualifier.
- The character-share breakdown of the system prompt (tool definitions at 4035 characters, roughly a third of one generation) is reliable as a share only. Characters divided by four overestimated the tokenizer's own count by about 24 percent on that generation, so absolute token counts derived that way are wrong.
- Whether the barge-in interrupt branch of the current instrumentation has been exercised on live traffic. Both recorded real calls report zero aborted turns, so that branch is proven only by the test suite and a diagnostic.
- The security posture of running business-tool code inside a builder was not assessed for any candidate in this pass. It is named as a decision to make deliberately, not as a solved problem.
