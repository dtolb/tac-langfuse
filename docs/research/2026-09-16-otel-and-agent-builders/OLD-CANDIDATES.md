### verdict refuted=True

CLAIM: Dify allows tool definitions AND their implementations to be authored inside the builder rather than in our application source, via four console-authored mechanisms: Code node (sandbox), Custom API tools (OpenAPI import), Workflow-as-tool, and MCP client — with a caveat about the sandbox's fixed dependency set and 15 s WORKER_TIMEOUT.

CORRECTED: Directionally right but overstated on the load-bearing point. Every file path, enum, service method and default cited is real (verified against langgenius/dify @ 9c6c48b, 2026-09-16), and the licence does not restrict any of it. But only ONE of the four mechanisms actually authors an *implementation* in the console: the Code node, whose `code: string` lives in the flow graph (web/app/components/workflow/nodes/code/types.ts, CodeLanguage = python3 | javascript | json — note `json` is a third member, and it is Jinja2 not JS/Py that also exists as a separate provider). Mechanism (3), workflow-as-tool, is not a separate authoring mechanism — it is the *exposure* path that makes a Code-node flow callable, and api/services/tools/workflow_tools_manage_service.py::create_workflow_tool requires an existing published Workflow **app** whose graph passes `WorkflowToolConfigurationUtils.ensure_no_human_input_nodes`. Mechanisms (2) Custom API tools and (4) MCP are DEFINITION-ONLY: api/core/tools/custom_tool/tool.py is a generic `ApiTool` that HTTP-requests a `server_url` via `core.helper.ssrf_proxy`, and api/core/tools/mcp_tool/ proxies a remote server. Both require the implementation to be written and hosted in our own application source — exactly what the claim says Dify lets us avoid. Same for PLUGIN tools (ToolProviderType.PLUGIN), which need a Python plugin package built outside the console. So the accurate statement is: definitions for all seven provider types (PLUGIN, BUILT_IN, WORKFLOW, API, APP, DATASET_RETRIEVAL, MCP) are registered in the console; only Code-node logic is *implemented* there. The caveat is also imprecise: `docker/volumes/sandbox/dependencies` does not exist in the repo — it is a bind-mount target Docker creates empty, and users drop a `python-requirements.txt` into it, so the dependency set is extensible-by-host-file, not fixed. Extending it, though, means editing files on the host and restarting the container — still outside the builder. The harder wall is not missing packages: `docker/volumes/sandbox/conf/config.yaml.example` carries a seccomp `allowed_syscalls` allowlist and an explicit `python_lib_path` list, which produces the recurring "operation not permitted" failures (issues #29843, #28974) and env-dependent import failures even for pip-installed libraries (#26704, matplotlib installed via python-requirements.txt, still fails on import). WORKER_TIMEOUT default 15 s is correct for docker-compose (`SANDBOX_WORKER_TIMEOUT:-15`), though the shipped config.yaml.example says `worker_timeout: 5` — the env var wins. ENABLE_NETWORK default true with HTTP(S)_PROXY forced to http://ssrf_proxy:3128 is correct. The claim's practical conclusion — long-running or exotic-dependency tools want to be HTTP tools pointed at our Node service — stands, and applies more broadly than stated, because the API/MCP/plugin routes were never console-implemented to begin with.

REASONING: I sparse-cloned langgenius/dify at main (9c6c48b, 2026-09-16) and read the cited files rather than docs. Confirmed: CodeLanguage enum (with a third member `json` the claim omits); api/core/tools/{custom_tool,workflow_as_tool,mcp_tool,plugin_tool,builtin_tool}/ all present; api/services/tools/api_tools_manage_service.py and workflow_tools_manage_service.py present with WorkflowToolManageService.create_workflow_tool at line 32; ToolProviderType enum listing all seven types; docker-compose.yaml service `sandbox` on image langgenius/dify-sandbox:0.2.15 with WORKER_TIMEOUT:-15, ENABLE_NETWORK:-true, HTTP_PROXY/HTTPS_PROXY to ssrf_proxy:3128, and volumes ./volumes/sandbox/dependencies:/dependencies. The licence (modified Apache 2.0) restricts only multi-tenant commercial operation and logo removal — nothing about tool authoring, and none of these four are enterprise/cloud-gated. So no cited fact is false. The refutation rests on the claim's own headline: "definitions AND their implementations ... rather than in our application source" applied to all four. Reading api/core/tools/custom_tool/tool.py shows ApiTool is a pure HTTP forwarder (do_http_request against api_bundle.server_url) and mcp_tool/ is a remote proxy — neither contains or hosts logic, so both fall under the stated refutation criterion "the mechanism requires writing code in our own application after all". ### verdict refuted=True

CLAIM: Flowise streams token-level model output incrementally over the network during an agent turn via SSE over HTTP POST /api/v1/prediction/{flowId} with "streaming": true; createPrediction sets the SSE headers and flushHeaders() before running the flow; no socket.io/WebSocket on the server; SSEStreamer writes straight to the Express Response; the post-tool-call answer is token-streamed, not buffered; AGENTFLOW is always streamable.

CORRECTED: Directionally correct and the mechanism is genuinely Apache-2.0 open source, but overstated in four ways.

(1) "AGENTFLOW ⇒ isStreaming: true" is not unconditional. `checkIfChatflowIsValidForStreaming` (packages/server/src/services/chatflows/index.ts:50-72) tests the chatbotConfig FIRST: `if (chatflowConfig?.postProcessing?.enabled === true) { return { isStreaming: false } }` — that return precedes the `chatflow.type === 'AGENTFLOW'` line. Enable post-processing on the flow and the whole POST falls into the non-streaming `return res.json(apiResponse)` branch. The claim quoted only the second check.

(2) Token streaming from an Agent node is gated on FOUR conditions, not on the endpoint. Agent.ts:1076: `const isStreamable = isLastNode && options.sseStreamer !== undefined && effectiveStreaming !== false && !isStructuredOutput`. So: the Agent must be the LAST node of the agentflow (an agent whose output feeds a Condition, another Agent, an Iteration node, etc. does not token-stream — it takes the `else` branch, `await llmNodeInstance.invoke(...)`, one buffered write); the model config's `streaming` must not be false; and structured output must be off. In the not-streamable-but-last-node case (Agent.ts:2418-2421, 2796-2799) the server still sends a single `token` event containing the ENTIRE answer — SSE-shaped, but not incremental. For a voice use case this is the difference that matters, and it depends on flow topology, not on the API call.

(3) It is SSE framing, not standards-consumable SSE. Every write is `'message:\ndata:' + JSON.stringify(...) + '\n\n'`. `message:` is not an SSE field name (the fields are event/data/id/retry), so a conforming parser ignores that line and delivers a default-typed `message` event whose data is the JSON envelope; the real event name lives inside the JSON payload. And because it is a POST, browser `EventSource` cannot consume it at all — you need fetch-with-ReadableStream or the flowise-sdk / flowise Python client. "Write your own client code" is therefore mildly required after all, though only an HTTP-client loop, not Flowise plumbing.

(4) "SSEStreamer writes straight to the Express Response" is true only in single-process mode. With `MODE=queue` the controller does `await getRunningExpressApp().redisSubscriber.subscribe(chatId)` before building the flow — the worker's token events cross Redis pub/sub first. That path has a repeated regression history (PRs 5884, 6008, and the 6083/6084 reverts of "fix: redis pub/sub and streaming response issue"; open issue 5363 on queue+streaming).

Those two frame names are available only to embedders who build their own filter spec. The docs' captured example ends at `nodeFinish`, consistent with this.

"during an agent turn" overstates it for looped/agent-shaped graphs. `getProcessorEvents` keys its delta cursor by node id alone and never resets it — `const previousIndexes = new Map<NodeId, number>()` … `previousIndexes.set(event.node.id, currentOutput.length)`, with no reset on `nodeStart`/`nodeFinish` and no `processId`/`index` in the key. A Chat node re-executed by a `LoopController`/`ChatLoopNode` tool loop therefore has its second-iteration deltas sliced against iteration one's final length, so early deltas of every turn after the first come out empty or truncated. Text mode is worse: `getSingleNodeStream` calls `controller.close()` on the first `nodeFinish` for the target node, so the stream ends after the first model completion and subsequent loop iterations are not delivered at all. Verified single-turn (as the docs show); multi-turn agent loops are not.

Also worth knowing about the cited evidence: `packages/docs/docs/cli/serve.md` is not fully trustworthy — its "Options" list omits `--stream` and `--stream-node` entirely, and it documents a "Single-Node Streaming Mode" via `--stream=NodeId` that `serve.ts` does not implement (the value of `args.stream` is only ever tested `!= null`; the filter spec is built from `streamNode`).

REASONING: Cloned Ironclad/rivet and read the implementing source rather than docs. The mechanism exists, is MIT-licensed, is in the OSS CLI (not an enterprise/cloud tier), and does put partial text on the wire before node completion — the claim's core is real. It fails as stated on three points: the emission is throttled at ~100 ms so it is not token-level; the CLI's filter spec omits `done` and `error`, so two of the five asserted frames are never sent by `rivet serve --stream` and the graph output/errors never reach the client; and the delta cursor in `getProcessorEvents` plus the `nodeFinish` close in `getSingleNodeStream` mean a repeated Chat node in an agent/tool loop streams wrongly or not at all after the first turn. Issue #185 ("Streaming of chat node output", closed) confirms `streaming.ts` is the maintainer's intended answer and that Graph Output nodes deliver in bulk — streaming is per-node partial output only. No open issues report the endpoint broken.
