# Can an open-source agent builder replace a hand-written agent behind ConversationRelay?

## 1. Scope, and what this page does not repeat

The system architecture, the anatomy of a turn, the Agent Connect assumption-and-reality tables, the OpenTelemetry ones, and the measured latency table are published at [agent-scaffold-architecture](https://pages-4296.twil.io/agent-scaffold-architecture), in sections `#architecture`, `#turn`, `#numbers`, `#tac`, `#otel`, `#proven`, `#rules` and `#verification`. The separate question of replacing the relay layer itself rather than the model behind it is argued at [convo-vs-livekit](https://pages-4296.twil.io/convo-vs-livekit); its architectural conclusions are cited here, and none of its figures were rechecked for this page.

This page asks one question. Can a self-hostable open-source agent builder replace a hand-written TypeScript agent while staying behind ConversationRelay and the Twilio Agent Connect SDK?

Three requirements do the filtering. The first is self-hostable open source in a local docker-compose stack, with no hosted control plane and no paid gate on a feature the design needs. The second is token-level streaming out of the runtime, because ConversationRelay synthesises speech from text arriving incrementally over a WebSocket, and a runtime that returns one finished string per turn puts the whole generation time into the caller's ear. The third is that tool definitions and their implementations are authored inside the builder rather than in the application's own source. Visual authoring quality, and whether a builder can retire the separate prompt-and-tracing service, are scored rather than used as filters.

Two facts about the SDK set the shape of every answer, and both were read from the shipped Agent Connect bundle rather than from documentation. `onMessageReady` is not the streaming path; it is the non-streaming auto-send convenience, and returning a string from it makes the SDK send one frame with `last: true`. The streaming path is `VoiceChannel.sendStreamingResponse()`, a public method whose only contract is an `AsyncIterable<string>`, which does one `ws.send` per chunk inside its own `for await` loop. That method is the integration seam, and it does not care whether the iterable is fed by a library call or by a socket read.

## 3. The fork, in three shapes

Shape (a) imports the builder's runtime as a Node library inside the existing process, so the prompt handler calls it directly and hands the resulting iterable to `sendStreamingResponse`. Shape (b) runs the builder as a separate container reached over a streaming HTTP body, with a generator in this process that reads frames and yields text deltas. Shape (c) moves nothing: the TypeScript agent keeps calling the model, keeps holding the WebSocket, and keeps dispatching tools, while the builder becomes the place a human edits the system prompt and picks which tools this version may use, publishing that as configuration the runtime fetches.

The seam is indifferent between (a) and (b), so shape (b) needs no new abstraction, only a frame reader and an abort forward. What it costs per turn is one request across a local bridge with a small body, plus whatever the builder does before its first model token. Against a healthy tool-free turn measured at 586 ms to 801 ms of model time to first chunk, from a handful of turns on one day with one caller and one model rather than a benchmark, and against a framework preamble measured at a ceiling of 84 ms taken from the worst turn of 33 generations on that same day with a range starting at zero, a single-digit-millisecond local hop is not the problem. Nothing in the protocol envelope is violated either: the reference publishes no deadline for the first text frame after a prompt and no time-to-first-token target, and its own example shows three token frames with the final flag on the third, so per-token sending is explicitly sanctioned. That local hop is unmeasured and is recorded as an open item, but it is not worth manufacturing a problem around.

The terms that do matter are different, and two of them are named candidates rather than transport physics. Windmill's tokens reach a client only through a database poll ladder of 100 ms for ten polls, 500 ms to poll 100, then 3 s, and the knob that would tighten it is behind the enterprise compile flag, which the vendor's own community image also excludes. Sim's live text is speculative and can be retracted after it has been spoken. Neither of those is latency in the network sense; both are the delivery mechanism refusing to be a token stream. The third term is the builder's own pre-model work, which is undocumented and unmeasured for every candidate on this list, and which is the number a spike has to produce.

Two hard constraints bind shape (b) regardless of candidate, and both were read from the shipped SDK bundle. The WebSocket connection handler requires a live local socket in a private map, and sessions are instance-local maps with no shared store, so the model can be remote but session truth cannot. And turns are serialised: the prompt dispatcher chains each turn's handler behind the previous turn's promise, so turn N+1's memory recall and prompt callback cannot start until turn N's handler resolves. That head-of-line property is exactly where an added network hop lands, and it is the single most important thing to know before adding one.

On abort, the draft was more worried than the code warrants. The streaming method breaks its loop on an aborted signal and resolves that signal as the caller's option first and its own active task second, and the interrupt handler cancels the task and sends the final frame itself when tokens have already gone out. So the local handler does return on barge-in even with no abort wiring. What an unforwarded abort costs is upstream billing and a runaway generation, not a stuck queue. Correcting one more claim from the draft: the SDK awaits memory retrieval before the prompt callback fires, so that recall is serial and upstream of anything the handler controls, and it is not inside the 84 ms preamble.

Which shape each candidate can take decides more than the fork itself. Only five candidates can be shape (a): Mastra, VoltAgent, Rivet, LangGraph JS and Node-RED. Of those, only Node-RED offers any in-builder authoring, and its authoring covers implementations while offering no first-party mechanism for tool definitions. Every candidate that fully satisfies requirement 3 is a separate service. So the fork is not a free choice between equals: requirement 3 forces shape (b), and shape (b) is where the trace breaks.

Shape (c) is the shape the scaffold already runs, with the incumbent prompt service as the authoring surface. Its prompt seam validates a JSON document edited in a web form against a strict schema, and that document carries the model identifier, the tool-choice mode, a step ceiling and the ordered list of enabled tool names alongside the prompt text. Changing the tool selection is a new version plus a label move, with no redeploy and no restart, and rollback is moving the label back. Requirement 2 stops applying to the builder in this shape, because the runtime that streams is the one already in the process. What shape (c) does not do is satisfy requirement 3: a person can rename a tool's description, reorder the selection, remove a tool from a version and roll the whole thing back, and cannot create a capability the repository did not already have.

## 4. The trace consequence

This deserves its own section because the instrument the whole latency argument rests on is produced by the model SDK running in this process, and moving the model out deletes it.

Grepping the shipped Agent Connect bundle for six strings, covering OpenTelemetry, async local storage, `traceparent`, tracer acquisition, W3C and propagation, returns zero matches for every one of them. The SDK carries no tracing. Every generation span in a trace today therefore comes from the installed AI SDK, and `gen_ai.client.operation.time_to_first_chunk` is a literal string inside that package. It is not in anything Twilio ships.

One spec detail makes the attribute less portable than it looks. The [GenAI semantic conventions](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-metrics.md) define time to first chunk as a histogram metric, and the span attribute for the same measurement is `gen_ai.response.time_to_first_chunk`. The AI SDK emits the metric name as a span attribute. So a builder that is specification-clean and does emit the measurement will emit it under a different key, and a query written against the current spelling reads nothing even in the good case. Those conventions are in development with no tagged release, so this should be rechecked rather than trusted.

Shape (a) costs the trace nothing, and that is the strongest position available. A library called inside the existing turn span inherits the parent from the ambient context and its spans reach the same exporter, so there is nothing to stitch. Mastra's bridge does exactly this, parenting under the active context. VoltAgent needs an explicit parent-span option, because its trace context deliberately deletes the ambient span to force a root and attaches the ambient one only as a link. Node-RED has no span model, so a single tree is reachable only by joining it in the host's own code. Rivet contributes no spans at all.

Shape (b) costs the trace two disconnected trees unless the builder both accepts the header and records the spans worth having, and only one candidate does both. Dify installs a composite propagator as the global textmap with an instrumented web framework and a parent-based sampler, and emits a span per workflow node. Langflow accepts the header and then drops the spans: its own source says all three signals deny by default on export, that the allowlist admits four scopes, that LLM instrumentor spans carry prompt and completion text and must never reach an operator's APM, and that the allowlist only ever subtracts, because a setting able to add a scope would reopen the leak the allowlist exists to close. Windmill captures the header at job push only, gated on a tracing variable, with the tracer initialiser returning nothing and the parenting function empty. Sim extracts only the trace id for log grepping and builds its workflow spans after the run finishes with backdated start times, so there is nothing live to parent. Coze produces a different failure: with zero occurrences of the string and no spans emitted at all, the result is not two trees but one tree with a hole in the middle of a turn.

What stops existing when the model call leaves is specific and no bridge recovers it: input and output token counts, cache read and cache write tokens, the model identity per step, the prompt and completion text, and the request issuance instant that makes time to first chunk meaningful. The prompt-version link goes too, for a reason particular to this stack: the trace store computes the prompt name and version only for observations typed as generations, so a span the bridge synthesises and types as a plain span carries the attribute and resolves to nothing. That behaviour was verified by reading the ingested rows directly, because this deployment exposes no public read API for traces and a 404 there means disabled rather than empty. A local trap compounds it: the span processor filters on export by instrumentation scope and by the presence of any attribute key beginning `gen_ai.`, so a span created with a bare tracer is created successfully, is visible to an in-memory exporter, and is silently dropped on the way out with no error anywhere.

What survives every shape is the number this repo already measures by hand: time to first token, anchored on the first non-empty text delta rather than on the SDK's first chunk, because a turn that opens with a tool call streams argument fragments with no audible output for hundreds of milliseconds. That measurement answers how long until the caller hears something. It does not answer whether a slow turn was the framework or the model, which is precisely what the vanished attribute answered in one query.

Shape (c) costs the trace nothing at all, including the tiled voice timeline, the per-turn generation spans and the prompt-version link. Its hybrid variant, where the builder also hosts business tools the runtime reaches over HTTP, costs one thing: a tool span with a real duration, real arguments and no children, so the time inside it is unattributed. On the measured scale, one tool returned in about 1 ms and another took 417 ms to 1018 ms across a small single-day sample because it queries a knowledge base over the network, so an opaque span in that second range is the shape to expect, in the middle of a turn a caller is waiting through. Closing that hole means the builder must accept a header on the tool call and continue the trace, and whether any surveyed builder does that was not checked. A second cost is concrete: the tool context passed to an implementation carries a conversation identifier, a logger and a profile identifier, and no abort signal, so on barge-in the model stream stops while an in-flight outbound tool call keeps running until it completes or times out.

## 5. The tools collision

The draft's inventory was wrong and its count contradicted itself, so here is the export list read from the shipped Agent Connect bundle. Nine exported functions produce tools: `defineTool`, `createMemoryRetrievalTool`, `createMemoryTools`, `createSendMessageTool`, `createMessagingTools`, `createStudioHandoffTool`, `createKnowledgeSearchTool`, `createKnowledgeSearchToolAsync` and `createKnowledgeTools`. Alongside them the bundle exports the `TACTool` class and a `BuiltInTools` map.

Nine functions is not nine tools, and that is why the count kept drifting. Three of the nine are factories of factories: the memory factory returns per-profile and per-session builders, the messaging factory returns a per-conversation builder, and the knowledge factory returns synchronous and asynchronous builders. All of them collapse to the four canonical identities in the `BuiltInTools` map: `retrieve_profile_memory`, `send_message`, `handoff` and `search_knowledge`. Everything else is `defineTool`, which is the generic constructor for a tool of your own and does no argument validation.

This scaffold adapts three of those nine functions today: the memory retrieval tool, the knowledge search tool and the Studio handoff tool. It writes three more tools of its own in TypeScript, and its measured prompt carries five tool definitions on a voice turn, because voice retrieves memory automatically rather than through the retrieval tool. So the shim count is three, and four if the messaging tool is ever enabled to let the agent send a message mid-call. That number is the same in every option below, and it does not change with the shape.

The detail that decides everything is that the SDK never invokes a tool. The `implementation` field is read in exactly two places in the whole bundle: assignment in the constructor, and the execute closure inside the adapter that converts a tool for one external agent SDK. The OpenAI and Anthropic conversions emit schema only. Tool dispatch belongs entirely to the model runtime. So the moment the builder becomes the model runtime, those tool objects are inert unless something re-exposes them.

The first option re-exposes them over HTTP or MCP. The `TACTool` objects keep being constructed, each implementation is wrapped in a route in this process, and they are registered in the builder as OpenAPI or MCP tools. The cost is three shims, four with messaging, a schema kept in two places, and one extra local hop inside the tool cycle. That hop is noise against a knowledge search measured at 417 ms to 1018 ms across a small single-day sample, and against a handoff measured once at 266 ms on one call, though a lookup that returned in about 1 ms would become dominated by it. This option keeps everything platform-side working and it obeys the standing rule about working with the SDK rather than around it. It does not satisfy requirement 3 for those tools: the definitions move to the builder and the implementations stay in TypeScript. That is the same limitation Dify's OpenAPI and MCP tools have, and the MCP paths in Langflow and Flowise share it.

The second option splits by ownership. The platform tools stay behind the first option's surface with implementations in TypeScript, and the business tools, the order-lookup and store-hours shaped things a non-engineer would actually add, are authored end to end inside the builder. One thing makes that split cheaper than it looks: memory injection does not depend on any of the memory factories, because the SDK awaits memory retrieval before the prompt callback fires and voice retrieves once per conversation, so the memory block arrives on the prompt payload and can be passed to the builder as an input variable. The cost is two authoring surfaces and an explanation of which is which.

The third option gives up the SDK-native tools: knowledge search becomes a REST call to the Knowledge API authored as an HTTP tool in the builder, and handoff becomes a REST or TwiML action authored the same way. That genuinely moves the implementations into the builder. It costs reimplementing two platform integrations, owning their failure modes, losing whatever the SDK fixes upstream, and breaking the standing instruction not to route around the SDK. It buys full compliance with requirement 3 at the price of the thing the scaffold exists to demonstrate.

Option two is the right trade, and the page should say plainly that requirement 3 is met for the tools a non-engineer would add and not met for the three platform ones, because the alternative is either a false claim or reimplementing the platform's own integrations to satisfy a rule.

## 6. Channel asymmetry, and which requirements apply where

Requirement 2 is voice-only by construction, and the draft argued the whole page as though it applied everywhere.

The streaming argument rests entirely on `sendStreamingResponse`, which is a method on the voice channel. The messaging and chat path is a different callback, whose signature was read from the shipped bundle and returns `Promise<string | null | void>`. There is no token sink in it, no writable, and no way to push a partial reply. The SDK's own handler checks whether the returned value is a string and, if so, sends one frame with the final flag set. That is exactly the one-string-per-turn shape used to eliminate Julep. So a runtime that cannot stream a token is indifferent on SMS and chat, and every candidate that fails requirement 2 becomes eligible on those channels.

Two smaller differences follow from the same signatures and both matter. The abort signal is required on the voice prompt payload and optional on the messaging callback, so the abort-forwarding mitigation in section 3 covers voice only. And the memory field is named differently on the two payloads, so code that reads the voice spelling reads undefined on the other half of the scaffold.

Stated as a rule: requirement 1 applies to every channel, because the licence and the compose stack do not care what a turn arrives on. Requirement 3 applies to every channel, because a tool is a tool. Requirement 2 applies to voice only. That asymmetry is load-bearing for the recommendation, because it means a candidate can be disqualified for voice and remain the best answer for the other two channels.

## 7. Failure modes the first pass never considered

The first of these dwarfs everything section 3 spends a paragraph defending, and it is the reason the recommendation changed.

Provider prompt caching depends on a byte-identical prefix. On one measured call the first turn's first generation took 3838 ms to first chunk against a cold cache, on a two-generation tool-calling turn with roughly 2520 input tokens, and the following turns on that same call reported cached input tokens and ran 0.51 s to 0.71 s. Those warm figures are turn two onward on a single call with one caller and one model and mean nothing quoted without that qualifier, and span durations do not sum to that cold turn because the tool fires as soon as arguments parse and overlaps the first generation. But the gap between those two states is a multi-second regression on the turn a caller forms an impression on, and a builder that rebuilds the system prompt per run, reorders tool definitions or injects a run identifier into the prefix turns every turn into that cold turn.

Two candidates do exactly that. Coze's reasoning system prompt has, as its third line before anything cacheable, a sentence stating the current time, filled per run at second resolution. That is a compile-time constant in Go, so removing it means forking the project and rebuilding the image; and the same template inlines retrieved knowledge chunks into the system message, so even with the timestamp patched the prefix churns whenever retrieval returns something different. VoltAgent appends a context block derived from the current user utterance to the end of the system prompt on every turn when a retriever is attached, which is structurally the same failure the scaffold's own uncapped memory block already walked into, with an explicit cache-breakpoint option as the documented mitigation.

Three candidates handle it well, and one of them treats it as a first-class design goal. Windmill's system prompt is the step's configured message verbatim, and its cache key is derived from the workspace, the runnable path and the step id with a source comment stating that keying on the step rather than the run is deliberate. Sim engineers it: cache-control breakpoints are placed on the last system block and the last tool definition, and its cache key is a hash of the workflow and block ids. Mastra documents cache preservation as a goal across four separate pages, and names the two ways to break it, a sliding message window that changes the start of the prompt as a thread grows and working memory living in the system prompt, each with a documented fix. Node-RED comes out well by doing nothing at all: the request body is read verbatim from a message property with no wrapper and no reordering, so stability becomes entirely the flow author's responsibility with no guard rail.

Conversation history drifting is the second failure mode, and it is real for most candidates. Mastra keys threads by its own thread and resource identifiers and re-sends a window per turn; Coze keys by its own conversation identifier, re-assembles up to a default of 100 rounds per turn, and has no flag to run statelessly, so it cannot be driven from this side's transcript at all; Windmill keys by its own memory identifier and re-reads from its database per turn, with a manual-messages mode as a clean escape; Sim owns history in its own store but keyed by an identifier the caller supplies, so there is only one copy; VoltAgent owns it keyed by its own identifiers with persistence suppressible per call; Node-RED owns nothing, because it has no memory abstraction. The concrete drift trigger for voice is barge-in: a turn this side truncates locally is still whatever the builder persisted server-side, and the model reads the builder's copy on the next turn. Pick one owner and make the other side advisory, and never run both alongside the SDK's own recall.

Concurrency is unmeasured for every candidate, and two have a named mechanism worth pricing. Windmill inserts one new database row per stream event, on the same database that runs its job queue, with a 20 s write timeout that logs and breaks, truncating the answer mid-sentence with no client-visible signal. Coze puts eleven containers in the request path, including a vector store, a coordination service, an object store and a three-process queue cluster, against three containers today. Sim's compose file gives the app an 8 GB memory limit and its behaviour under simultaneous calls was not tested. A demo with two simultaneous calls is a plausible demo, and nobody has a figure for it.

Text destined for speech synthesis is the fourth, and it is easy to overlook because it works fine in a chat window. ConversationRelay synthesises whatever arrives in the token string, and markdown, emoji and bullet lists arrive intact; SSML passes through, but with the default TTS provider only one element is honoured and only for one language. Nothing in the protocol strips anything. Stripping in the bridge splits into two very different implementations: a character filter that drops emoji and stray punctuation can run per chunk with no lookahead and costs nothing, while a real markdown parser needs lookahead across chunk boundaries and therefore re-buffers, which defeats requirement 2 to fix a cosmetic problem. Prefer the character filter, and prefer prompting against markdown in the first place. One candidate makes this worse by default: Coze emits reasoning deltas as delta frames on the same stream sharing the answer message's identifier, so a naive consumer synthesises the model's chain of thought to the caller.

The fifth cost is this repository's own guard suite, and it is unaccounted anywhere in the first pass. Five vendor-boundary rules are enforced by a test that reads import strings across the server, shared and web trees, and separate tests assert that no logging bypasses the scrubbing hook, that the shared directory imports nothing outside itself, that every environment variable read appears in the example file, and that the compose file lists every path prefix as a literal. Above those sit tripwires that assert the rule set is intact, because the failure mode of a guard is not a false alarm, it is passing silently forever. Two of the five vendor rules invert under any runtime move. The rules restricting the AI SDK and its provider package to one model directory stop describing anything once the builder is the thing that calls the model, and a builder that is itself an AI SDK wrapper means the rule has to be rewritten to name the builder's package rather than deleted. The rule restricting the trace client to the prompt directory survives only if the incumbent prompt service stays. The two rules keeping the Twilio packages inside the adapter directory survive untouched in every shape, because the channel seam does not move, and that is the one piece of good news. Shape (b) adds a further loss that is not a test: the Twilio-free bench exercises the turn function end to end in this process, and moving the model out moves the thing being proved out of the process the bench runs in.

## 8. The recommendation

The recommendation changed, and both of the draft's picks are out for reasons the first pass did not check.

Langflow is out because it drops the spans the scaffold exists to demonstrate, by design and by policy. Its own source says the LLM instrumentor spans carry prompt and completion text and must never reach an operator's APM, and that the export allowlist only ever subtracts, because a setting able to add a scope would reopen the leak the allowlist exists to close. Adopting it as the model runtime means the per-turn generation spans cannot be reconstructed from either side: not from Langflow, which drops them at export and forbids widening the filter, and not from a bridge, which never sees the model call and cannot invent token counts, cache behaviour or the model's own first-chunk instant. What arrives in the joined trace is one flow-execution span wrapped in HTTP and database spans. For a scaffold whose purpose is per-turn tracing, that is close to disqualifying. Its second problem is that browser-authored Python is executed in the server process and cannot be sandboxed, because the sandbox module is imported only by the two Python-REPL components.

Sim is out for voice, on a mechanism nobody had looked for. Its live text is speculative: because a provider reveals its stop reason only at turn end, text streamed during a turn may turn out to have been preamble before a tool call, and Sim then sends a reset frame meaning discard everything accumulated for this block because the final turn will re-stream. Synthesised audio cannot be unspoken. So on a tool-calling turn the caller hears a preamble and then hears the real answer, with no way to retract the first. The three ways out all cost the thing the header bought: accept occasional double-speak, drop the header and receive the whole final turn in one frame, or buffer until the turn is classified and reintroduce the latency. Its second problem is licence shape: the proprietary tree is imported at boot and on every tool call, the vendor's own README in that tree says the directory is required at build time, and its grant covers non-production use only.

**Primary: Mastra, in shape (a), with requirement 3 explicitly bending.** It is the only candidate that satisfies requirement 2 at the exact shape of the seam with no transport at all, because `agent.stream()` returns a `ReadableStream<string>` that the voice channel's method already consumes. It is the only candidate that keeps the trace whole for free and replaces the vanished instrument rather than deleting it, because its bridge parents spans under the ambient context in process and its exporter emits current GenAI conventions including input and output messages, system instructions, tool definitions and cache read and creation token counts. Its prompt prefix is stable by design with cache preservation stated as a goal, and the two documented ways to break it are the two traps this scaffold already fell into, each with a documented fix. And its Editor versions the prompt and the tool selection as one snapshot, with draft, publish, restore-into-draft, per-request version selection with no redeploy, and deterministic JSON on disk for pull-request review, which is a strict superset of what the scaffold has today, since the incumbent versions the prompt but not the tool set.

What fails is requirement 3, on the vendor's own words, that collaborators choose from the tools available to the Editor but cannot implement new tools in Studio. That was verified against the API rather than accepted from prose: the server exposes list, read and execute routes for tools and no create route, and the enterprise Agent Builder's tool field is an allowlist of ids matched against registered tools at request time. Its code mode has the model write TypeScript at inference time, and its scaffolding agent writes TypeScript into a repository that then needs review and a restart. None of those is builder-authored tool implementation, and none of them should be stretched into a pass.

Four conditions attach to the recommendation. The console must sit behind authentication on a path that is not part of the public demo surface, because the surface that edits prompts is also the surface that decides what the agent may do. The enterprise Agent Builder must not be deployed without an agreement, and note that the licence check fails open when its validation endpoint is unreachable, which makes this a compliance question rather than a technical gate. Orchestrate the turn as an agent and not as a workflow, because workflow streams carry lifecycle events rather than token text. And pin versions tightly: minor releases land weekly on a 1.x line, the repository carries compatibility shims for older core versions, and the Editor, the piece this recommendation leans on hardest, ships on an alpha version string.

**Runner-up: Windmill, in shape (b), and it wins when requirement 3 cannot bend.** It is the runner-up rather than Langflow or Sim for four reasons that survived verification. Its in-builder tool authoring is the strongest in the field, with a tool's source living in the flow value, written in the flow editor, and running as a real job under the normal language executor. Its prompt prefix is byte-stable by explicit design, with a source comment reasoning about provider cache keys. Its inline path versions the prompt, the tool selection and each tool's source code as one flow artifact, with an Apache-2.0 flow specification and CLI extraction that round-trips tool code to a reviewable tree, so a prompt change and a tool-code change land in one commit. And the AI agent step, its tool loop, its streaming events and its memory carry no enterprise gate at all.

The condition under which the runner-up wins is specific. Requirement 3 must be genuinely immovable, and either upstream must replace the poll loop with a push transport or ungate the settable poll delay, or the enterprise licence must be bought, which resolves requirement 1's paid-gate failure and requirement 2's cadence together and also restores OTLP export. Without one of those, tokens arrive in roughly 500 ms clumps after the first second, only the terminal flow step streams, streams end at 60 s so reconnect and resume become this side's code, and the per-generation attribute disappears with nothing to replace it because the string `gen_ai` appears nowhere in the backend. If it is adopted, use inline agents rather than reusable ones, because a reusable agent resource resolves live rather than pinned so a run is not a snapshot, and pass this side's history through the manual-messages mode to keep one transcript.

**A third position worth naming, because section 6 creates it.** If voice is out of scope, or the SMS and browser channels are cut over first, Sim becomes the best answer, because requirement 2 does not apply where the callback returns one finished string, the reset frame is harmless when a final reply is assembled before sending, and Sim's deployment snapshot is the best versioning surface of the twelve. That is a real option for two of three channels and should not be discovered by accident later.

**What a spike must prove**, in the order that kills candidates fastest, with each step being one query rather than an investigation. Count the distinct trace identifiers belonging to one call: one means the trace is whole, two means it is not, whatever the documentation says. Check that the parent span identifier of the builder's topmost span equals the span identifier of the turn span, because a shared trace identifier with a missing parent renders as a separate root. Search every span in the tree for a time-to-first-chunk attribute under both spellings, the metric-style name the AI SDK emits and the span-style name the conventions define, and for any token usage attribute at all; a null answer here is the finding. Compare cached input token counts on the first turn against a later turn in the same conversation, which catches the failure no header can fix. Measure the interval from the request write to the first non-empty text delta, minus the model's own time to first chunk measured separately from the same host, and report it as a distribution over roughly thirty turns rather than a mean. Confirm that a barge-in stops the builder's upstream generation, verified from the builder's own logs rather than from the local loop exiting. And confirm that a tool authored entirely in the builder can call the platform-tool surface and return a result the model uses. Compare against the 586 ms to 801 ms tool-free baseline and the 84 ms preamble ceiling, both from one day with one caller and one model, and never against the one call that landed inside a measured two-hour upstream slow window where a tool-free turn took multiple seconds, because those numbers describe the provider that afternoon and nothing about this architecture.

**Migration cost, in files and phases.** The agent core is sixteen TypeScript modules; the channel adapter is seven, and none of them moves in any shape, because the WebSocket must terminate here. Phase one is a bench-only spike with no Twilio, standing the builder up behind the existing model port and driving three turns through the browser bench, which proves the streaming shape and the prefix stability without spending anything. Phase two runs both runtimes behind a flag, with the prompt version selecting which, so voice can be cut over one conversation at a time and reverted by moving a label. Phase three moves the business tools into the builder and leaves the three platform adapters untouched. Phase four retires the hand-written loop and rewrites the two vendor rules that no longer describe anything, adjusting the tripwire's minimum count deliberately rather than lowering it to make a test pass. Phases one and two are where the decision actually gets made; phases three and four are only worth starting once the spike returns one trace identifier and a stable prefix.

## 9. What nobody should adopt, and why

Every candidate eliminated in the table gets a verdict here, so a reader who skims does not have to reconstruct one.

Dify fails requirement 1 on two counts: the licence is a modified Apache with added conditions that GitHub reports as NOASSERTION and that is not OSI approved, and part of the stack the agent node needs ships only as a prebuilt image with no public source, so a required component is a binary. Its streaming is also uneven, with the reasoning-loop runner emitting the whole final answer as one chunk. Its trace behaviour is the best of the out-of-process candidates, which makes the licence the sharper loss.

Flowise fails requirement 1 on licence ambiguity that is not confined to an optional wing, because the server entry point imports enterprise middleware unconditionally at boot and the carve-out extends open-endedly to files carrying a copyright notice. Separately, it has no versioning at all: the chat-flow entity has no version column and no history table, and saving overwrites the flow data in place, which is disqualifying for a scaffold whose headline is versioned prompts.

Rivet fails requirement 2. Its chat node coalesces partial output on a timer defaulting to 100 ms, its delta cursor is keyed by node id and never reset so the second iteration of a tool loop is sliced against the first iteration's length, and text mode closes the stream at the first node-finish event. It is the cleanest licence and the cleanest in-process shape on the list, and it has seen no feature release in roughly fifteen months.

Letta Code fails requirement 3, because mods are TypeScript files on the harness machine rather than anything a builder hosts, and they only help if the agent runs inside that harness. Its prompt provenance is genuinely good and points the wrong way for this purpose: the agent rewrites its own memory blocks, so the prompt is committed by the agent rather than approved by a human, which is the opposite of the approved-version-per-release model.

LangGraph JS with Studio fails requirement 1 on Studio, which has no source repository and no package, opens a hosted URL, and lists a hosted account and API key as prerequisites, with a self-hosted platform available only as an enterprise add-on requiring a purchased key and egress to a vendor endpoint. It also fails requirement 3, because Studio has no code editor and no execution runtime, and its assistant configuration is selection.

Coze Studio passes all three requirements and should still not be adopted. The system prompt template states the current time at second resolution in its prefix, so provider prompt caching never hits and every turn is a cold turn, in a compile-time constant that cannot be configured away. Tracing does not exist in the open-source build: its two trace read handlers bind their request and return an empty struct with HTTP 200, so the UI's trace panel is wired to endpoints that return nothing, and every OpenTelemetry module is an indirect dependency. It cannot be driven statelessly, so a second conversation history is unavoidable. Its public chat request cannot pin a version. Engineering has largely stopped, with four commits over five and a half months, a latest release seven months old, and [CVE-2026-7023](https://nvd.nist.gov/vuln/detail/CVE-2026-7023), a SQL injection with a public proof of concept, reported against that latest release. Its visual authoring is the best verified anywhere in this sweep, which is exactly what makes the rest easy to overlook.

VoltAgent fails requirement 3 outright: tools are a schema plus an execute function in TypeScript you host, and no route creates an agent, prompt or tool. It also cannot retire the incumbent prompt service, because the versioning console is not self-hostable below the top commercial tier and the free tier allows one prompt, and tool selection is never versioned with a prompt in any case. Two migration costs are specific: it emits no `gen_ai` attributes and does not pass the AI SDK's telemetry option, and its trace context deliberately deletes the ambient span to force a root, so a single tree requires in-process embedding plus an explicit parent-span option.

Node-RED is the best in-process shape and the strongest implementation-authoring story in open source, and it is not an agent builder. There is no tool-definition mechanism in core: 37 nodes across six categories with nothing LLM-shaped, so surfacing a name, description and argument schema to a model needs either a small third-party package or an adapter in your own source. The streaming capability lives entirely in one third-party node by one maintainer, and because its streaming branch returns nothing assembled, tool-argument reassembly and message-history accumulation are also your code. There is no span model, so the trace regresses to hand instrumentation. Adopting it is less replacing the hand-written agent than re-expressing it visually.

Langflow and Sim were the first pass's primary and runner-up, and both were demoted in section 8: Langflow for dropping the generation spans by design and executing browser-authored Python unsandboxed in the server process, and Sim for retractable spoken text plus a proprietary tree that runs at boot and on every tool call under a non-production grant.

Beyond the twelve, several licences fail requirement 1 before any capability question arises. n8n moved to the Sustainable Use License and says itself that it is source-available rather than open source, with use restricted to internal business purposes and a separate licence file for enterprise paths. Arize Phoenix is Elastic License 2.0 for the server, with only its OTel package under Apache, and third-party lists calling the whole thing Apache are wrong. Open WebUI is BSD-3-Clause with an added branding clause, reports NOASSERTION, and concedes it is not OSI approved. FastGPT adds a no-SaaS variant and Typebot uses the Functional Source License. Activepieces is the textbook open-core failure for this use, with an MIT core, a commercial licence over its enterprise packages, and agents and chat explicitly excluded from the Community Edition, which is precisely the capability needed. Botpress self-hosting is sunset, so it is SaaS-only in practice, and PromptLayer has no self-host at all.

A whole category is mistaken for agent builders and fails requirement 3 by construction, because these tools observe or store prompts and do not orchestrate or execute tools: Agenta, Opik, Lunary, Helicone, PromptLayer and Phoenix. Arize states the principle in its own words, that it deliberately did not build prompt management because applications depending on an observability tool at runtime is an ill-advised design. Pezzo is dead, with its last release in May 2024 and an archived examples repository. Latitude relicensed to MIT and pivoted to monitoring, so its current repository is trace search and redaction rather than an agent builder. Any of these could replace part of the incumbent trace service, and none replaces the agent. Note the one twist section 6 introduces: in shape (c) this category stops being disqualified, because a tool that cannot stream a token is a perfectly good place to write a prompt.

Retired or dormant projects to leave alone: Microsoft Prompt Flow, whose feature development ended with runtime images frozen including security updates and whose successor is a code SDK rather than a builder; AutoGen Studio, since its parent has been in maintenance mode and Studio's declarative model can only express serialisable properties, so callables and hooks cannot be authored in the UI; Superagent, whose organisation pivoted to AI security; and Inferable, whose last commits across its repositories are from early 2025 with siblings archived.

Wrong-shape candidates worth naming so nobody re-litigates them: Julep, which is otherwise a genuine contender with Apache-2.0, a compose stack and a real tool system, and whose own [FAQ](https://docs.julep.ai/FAQ) states that streaming is planned and not implemented; Chainlit and CrewAI Studio, which are front ends over code you write; Kestra, whose execution model produces task outputs rather than token deltas; RAGFlow, a strong retrieval product whose design centre is neither tool authoring nor streaming to an external relay; and Vapi and Bland, neither of which is open source.

Finally, Pipecat, LiveKit Agents and Vocode are permissively licensed and self-hostable, and they own speech recognition, synthesis and interruption, so they replace ConversationRelay rather than sitting behind it. Pipecat Flows is the only genuinely visual voice-agent authoring tool in open source, which makes it worth a deliberate decision rather than a dismissal. That decision is argued at [convo-vs-livekit](https://pages-4296.twil.io/convo-vs-livekit), including the point that the alternative's own telephony quickstart tells you to connect a Twilio SIP trunk, and the counted move from vendor-run conversation services to customer-operated subsystems.

## 10. Open items

Nothing in this section is a hedge on a number quoted above, because every figure carries its caveat where it is used. These are the claims resting on documentation rather than measurement, and the questions left unsettled.

Nothing here was run. Every candidate claim comes from reading source at a named commit or from published documentation, and no container was started, no call was placed against any builder, and no token cadence was observed on any wire. Every latency figure is transcribed from this repository's own recorded measurements rather than re-measured for this page.

The transport cost of shape (b) across a local bridge was never measured, so every statement that it is small relative to model time rests on the measured model figures plus an unmeasured assumption that a small-body local request costs single-digit milliseconds. No candidate's internal pre-model latency was measured either, so no candidate can yet be compared against the 84 ms preamble ceiling. For the primary recommendation specifically, the in-process interval from the stream call to the first text delta is unmeasured, and it is the single number that decides viability on the voice path. It is also unknown whether the awaited stream promise resolves before the first chunk or only after upstream setup, which on voice is the difference between a memory read costing time to first audio or not.

Whether any surveyed builder produces a byte-stable system-prompt prefix across turns is untested against any of them. The prompt-cache failure mode is reasoned from how prefix caching works plus this repository's own measured cold-versus-warm gap on a single call, which is why it is a spike step rather than a finding. Related and unresolved for the primary recommendation: whether serialised tool definitions keep a stable order across runs, since reordering would defeat caching just as surely as an unstable prompt.

Whether ConversationRelay buffers text to sentence boundaries before synthesis is inference from the Voice Insights definition of one latency event, as time from receiving a text sentence to the start of audio synthesis, and it is never stated as a protocol rule. The conclusion that per-sentence chunking would be inaudible is therefore unproven and should not be used to excuse a coalescing window. The reference also publishes no WebSocket idle timeout, no deadline for the first text frame after a prompt, no time-to-first-token target, and no numeric value behind its maximum-call-duration or concurrency errors, and absence of documentation is not proof of absence. Whether queued-but-unspoken tokens are discarded on interrupt is not stated on any reference page.

Every negative traceparent verdict for Flowise, Letta, Node-RED and Coze rests on a repository code search returning zero matches for the string on the date read. That method covers source and tests and would miss a capability provided entirely by a dependency, so those are strong rather than proven negatives. For Sim it was established only that the route wrapper extracts a trace identifier for logging and that real propagation exists on an unrelated path; whether a workflow run could be made to parent its block spans to an inbound header was reasoned about and not attempted. For Windmill it is unresolved which parts of the trace pipeline work in a plain open-source build and whether the relationship to an inbound trace ends as a parent or as a link. Whether the enterprise build's spans carry prompt or completion payloads at all is unknown, because the sources are not in the repository.

The primary recommendation's trace claim is read from an example's documentation and from the presence of a propagation module and its unit test, not from running the example, so the parent-and-child assertion is claimed by the project rather than measured here. Its two open tool-buffering defects were read from the issue tracker with version-pinned reproductions, and their effect on a voice turn where a tool result should reach synthesis the moment it exists is not quantified. The granularity of its payload-suppression policy is unread, so whether a generation span can be exported while withholding prompt text is unknown. Whether its memory can be omitted entirely while still resolving stored Editor versions looks supported and was not verified.

Several documentation-only claims sit behind the eliminated candidates and are recorded so nobody re-derives them. Whether Coze's current guards close the SQL-injection advisory was not established, and the advisory should be treated as open against the latest release. Two measurement disagreements inside this repository's own record are published rather than averaged, because both are real. The memory block's share of the system prompt is 52 percent against a denominator of the base prompt plus memory, and 35 percent once the roughly 4035 characters of tool definitions are included, and the source does not state which denominator it intended. Prompt-share percentages are characters divided by four, a method that predicted about 3132 tokens where the tokenizer reported 2520 on the same generation, an overestimate of roughly 24 percent, so the shares are reliable and absolute token counts derived that way are not.
