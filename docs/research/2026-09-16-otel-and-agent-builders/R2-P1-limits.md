## 3. What it cannot see, how it fails, and whether it belongs upstream

### 3.1 The three things this design cannot give you

Everything in the previous section is measured by a Node process that receives text frames over a WebSocket and sends text frames back. Three quantities a voice engineer actually wants sit on the other side of that boundary, and no amount of span work in this process will produce them.

**Speech synthesis time.** ConversationRelay accepts `{"type":"text","token":"…"}` frames and turns them into audio inside Twilio. The protocol's app-to-Twilio message set contains no acknowledgement of any kind, so the moment a token becomes sound is never reported back on the socket ([WebSocket messages reference](https://www.twilio.com/docs/voice/conversationrelay/websocket-messages)). Twilio does measure it: the Voice Insights ConversationRelay event `tts_latency` is defined as the time from receiving a text sentence to the start of audio synthesis ([Insights events reference](https://www.twilio.com/docs/voice/voice-insights/api/call/details-conversation-relay-events)). That definition is also the only public hint that Twilio aggregates tokens to sentence boundaries before synthesising, and the hint is all it is, because no protocol page states an aggregation rule. Treat sentence-level buffering as an inference from a metric definition, not a documented contract.

**Audio playback time.** The same asymmetry, one step further downstream. The `<ConversationRelay>` TwiML verb exposes an `events` attribute whose documented values include `speaker-events` and `tokens-played` ([TwiML reference](https://www.twilio.com/docs/voice/twiml/connect/conversationrelay)), which sounds like the missing signal. It is not reachable through the SDK as shipped. In the 2.2.0 bundle the inbound validator `WebSocketMessageSchema` is a union of exactly `SetupMessageSchema`, `PromptMessageSchema` and `InterruptMessageSchema`; a frame that fails that union is debug-logged and dropped, and a frame that parses but carries an unrecognised `type` reaches a `default:` branch that logs `Unhandled WebSocket event type` and returns. The strings `tokens-played` and `speaker-events` appear in the bundle only inside the doc comment on the TwiML `events` field, never as message types. Version 2.3.0 widens that union by one member, for DTMF keypresses, and nothing else ([release v2.3.0](https://github.com/twilio/twilio-agent-connect-typescript/releases/tag/v2.3.0), [PR #96](https://github.com/twilio/twilio-agent-connect-typescript/pull/96)). So subscribing to playback events in TwiML today delivers frames that the SDK discards before any consumer callback runs. The residual is visible in the trace as an unattributed tail: on the one instrumented call whose root span covered 42675 ms, the interval from the final end-of-turn marker to socket close was 2394 ms of the caller still hearing the last reply plus hanging up, and nothing this process owns can look inside it. That figure is one call with one caller in one direction, so read it as an existence proof rather than a typical value.

**Speech recognition endpointing.** Twilio owns transcription end to end. The application influences it only through TwiML at call setup, through `transcriptionProvider`, `speechModel`, `hints`, `deepgramSmartFormat`, and the endpointing knobs `speechTimeout` (600 to 5000 ms, default `auto`) and, on one provider model, `eotThreshold` and `partialPrompts`. Raw audio never reaches the application, so the interval between the caller falling silent and the `prompt` frame arriving is a Twilio-side decision the process observes only as its outcome. This is why the first timestamp any span in this design can honestly claim is the instant the `prompt` callback entered, which is a floor and not the caller's stop. Two further delays hide beneath even that floor, both visible in the shipped bundle: `handlePromptMessage` awaits memory retrieval before invoking the consumer's `onPrompt`, and prompt frames for one conversation are serialised through a private promise chain, so turn N+1 cannot begin until turn N's handler resolves.

The tempting mistake here has a specific shape, and this design fell into it before catching it. A server-side proxy for time to first audio, anchored on the first non-empty text delta leaving the socket, landed within 0 to 3 milliseconds of time to first token on all six turns of the one instrumented call (2667 against 2664, 484 against 481, 1201 against 1201, 1655 against 1654, 547 against 546, 3499 against 3498, all in milliseconds, one call, one caller, one direction). That agreement is real and it is worth having, because it proves a negative: the SDK's `sendStreamingResponse` performs a synchronous `ws.send` inside its own `for await` loop, so nothing queues between the model stream and the socket. What it does not prove is anything about audio. The two numbers agree precisely because they measure the same event twice on the same side of the boundary. Presenting that proxy as time to first audio publishes a figure that excludes synthesis, network transit and playback, which is the entire part a caller hears.

To get the real numbers a reader has to leave this process. Voice Insights publishes the ConversationRelay event family, which includes `stt_latency` and `tts_latency` with a `latency_ms` field, `first_token_received` (documented as marking the end of application latency), `final_token_received` with `total_tokens` and `total_words`, and start and end events for both agent speech and customer speech. Those events are emitted at the carrier edge, so a query that does not scope itself to that edge returns nothing at all. The alternative, `mark` events on a Media Streams connection, means adopting a different TwiML verb and leaving the managed relay path, so it is a replacement rather than an addition.

Where the protocol documentation is simply silent, this page says so rather than estimating. No public page fetched during this work states a deadline for the application to send its first `text` frame after a `prompt`, a WebSocket idle or ping timeout, any time-to-first-token target, the numeric maximum call duration behind error 64104, or the numeric concurrency limit behind 64109. No page states whether tokens already sent but not yet spoken are discarded when a barge-in arrives; the only observable contract is `utteranceUntilInterrupt`, the text the caller actually heard, from which the truncation point is inferred. Absence of documentation is not absence of a limit, and none of those gaps is filled with a guess here.

### 3.2 One span family is a blend, and reading it as caller speech will mislead you

The tiled timeline in the previous section alternates two span families with no gap between them. One of them, the family covering everything between the end of one bot response and the arrival of the next `prompt`, was 27622 ms of a 42675 ms root span on the instrumented call, which is 65 percent of the call. That is a single call with a single caller in one direction, and it is the largest number this design produces, which makes it the most likely to be quoted badly.

It cannot be read as how long the caller talked. Four distinct things live inside it. The bot's own audio is still playing at the start of it, because playback continues past the last token this process sent, as the 2394 ms tail above shows. The caller then speaks. Recognition endpointing adds its configured silence window after the caller stops, which by default the application does not even choose. And on the first turn of a conversation, the SDK's memory retrieval round trip lands inside it too, because retrieval is awaited before the consumer's prompt handler is invoked and voice runs retrieval once per conversation, so that network call sits in the preceding interval rather than in the turn it serves.

Local token streaming, by contrast, was 150 to 804 ms per turn on that same call, which is the measurement that establishes the 65 percent is not this process being slow. The honest description of the blended span is a coverage device: it exists so that the sum of the root's children equals the root, which turns "where did the time go" from an investigation into a subtraction. It is not a caller-behaviour metric, and any dashboard that averages it is averaging four unrelated things.

Worth knowing for anyone designing this from scratch rather than copying it: the OpenTelemetry GenAI conventions have an open, unmerged proposal that arrives at the same shape independently. It argues that a live session streaming audio in both directions cannot be represented by a single client-timed inference span, models the session as events correlated by `gen_ai.conversation.id` rather than as a span, and proposes an opt-in span for user input bounded by voice-activity events ([PR #394](https://github.com/open-telemetry/semantic-conventions-genai/pull/394)). A separate open proposal introduces an end-reason attribute intended to capture barge-in as a turn outcome ([PR #390](https://github.com/open-telemetry/semantic-conventions-genai/pull/390)). Neither is merged, so this is convergent prior art rather than conformance, and both should be re-checked before anyone builds on them.

### 3.3 Failure modes

Broken telemetry rarely announces itself. The characteristic symptom is a trace that looks complete, because the span that went missing is one nobody counts. Every row below was hit during this work.

| Assumption | Reality | Symptom you would actually see |
|---|---|---|
| A span created with a plain OpenTelemetry tracer reaches the backend. | The vendor span processor filters by span type, admitting spans from its own tracer, spans carrying a `gen_ai.` attribute, and spans from instrumentors it recognises. Everything else is dropped on export. | The turn span is absent while the model spans beneath it arrive, so the trace renders as a set of orphans and looks like a parenting bug rather than a dropped export. |
| Custom attributes can be set at the top level of a span. | The vendor attribute builder destructures a fixed key set and discards the rest silently. Custom keys must nest under metadata. | The attribute is set without error, the span arrives, and the field is simply not there. Nothing logs. |
| Setting a metadata value to null records a null. | The serialiser keeps a key only if the serialised value is truthy, so null and empty string vanish while false and zero survive. | A field that means "measured, and the answer is nothing" is indistinguishable from a field that was never written. |
| A span that is created will be exported. | A span that is never ended is never exported at all. | The child spans arrive and their parent does not, so the trace has a hole exactly where the summary attributes live. |
| Flushing the tracer provider before exit works. | The globally registered provider is a proxy with no flush method, so the obvious call is an optional-chained no-op. The flush has to go through the delegate. | Short-lived processes and scripts produce an empty backend with no error on either side. |
| A signal handler in the preloaded instrumentation module can shut the SDK down. | A preload's signal listener runs before the application's own, so provider teardown races the code that ends the root spans, and a span ended on a torn-down provider is dropped in silence. | Roots go missing on clean shutdown but not in development, which reads as an export problem rather than an ordering problem. |
| The barge-in handler is the right place to close the turn span. | The interrupt callback fires immediately after the stream task is cancelled, while the turn's own completion still needs the stream drain, and attribute writes after a span ends return early without error. | A barged-in turn appears in the trace with no output text, no tool list and no total, on the one turn ending that is ordinary operation for a phone call. |
| The barge-in handler at least inherits the ambient trace context. | The SDK dispatches that callback from its own WebSocket message handler, so there is no active context to inherit. | Every barge-in produces a second, single-span trace, and the call's own trace looks like the interrupt never happened. |
| Taking ownership of when a span ends is free. | The vendor helper sets error status and then ends the span, so a caller that ends it first loses the status. | A turn whose prompt fetch threw exports with an unset status and no message, and error-rate panels read clean while callers heard a failure. |
| The prompt-version link is carried on telemetry metadata, as in older recipes for this model SDK. | The current major version has no metadata field on its telemetry options at all, and the link object must be a plain object with a numeric version rather than the JSON string the prompt client's serialiser returns. Neither half errors. | The prompt version's metrics view stays empty, which reads as a problem with the tracing backend. |
| A hand-set prompt link on any span will be picked up. | The backend computes the prompt name and version only for generation-type observations and writes null for others. | The attribute is present and correct on the wire and absent in the product, verified by inspecting the datastore directly. |
| Starting an observation makes it the active span, so nesting follows the code. | The vendor's start helper creates an observation without activating it, so a span opened alongside a model call does not contain it. | A published waterfall diagram shows the wrong tree, and the reader who copies it cannot reproduce it. |
| A test with an in-memory exporter proves the pipeline. | An in-memory exporter sees spans the real processor's filters would drop, and a bare tracer provider without an async context manager makes context activation a silent no-op. | Tests pass, and the first live run reports six trace identifiers for one call. |
| The tracing backend's absence of trace data means no traces were recorded. | In this configuration the public read endpoints for traces return 404 because the read API is disabled, not because the store is empty. | An automated verification step reports zero traces while the traces are plainly visible in the user interface. |
| The instrumentation is running because the code is committed. | The container image copies source at build time rather than mounting it, so a code change reaches production only on rebuild. | A real call placed against an image built hours earlier comes back missing every new span, which reads as "the instrumentation does not work" rather than "the code was never deployed". Check the image build time against the commit before anything else. |
| Restarting the container picks up the changed configuration. | A restart re-runs the container with its original environment block, so the change silently does not take. Recreation is required. | The variable is set on disk, the process disagrees, and every hypothesis you form next is about the wrong layer. |
| A running process picks up the fix. | This runtime does not hot-reload code, though prompt edits fetched from the tracing backend do land live within a cache interval. | A verification run reports the old behaviour because the process predates the fix by an hour, and the fix gets reverted as ineffective. |
| Awaiting anything between the turn function resolving and the token drain is harmless. | The budget is one macrotask. One resolved-promise await still wins; two lose, and so does any await that itself awaits. | Time to first token and turn total report null while the caller hears the entire answer, because the timing span closed before the stream drained. |
| A per-conversation timeline can be keyed by conversation identifier alone. | A handler can outlive the start of the next turn, and orchestrated conversations reuse one identifier per caller profile. | The straggling handler closes the wrong turn: one turn exports with a 10 ms duration carrying the previous turn's timings, and its own close silently no-ops. |
| The model SDK's span and attribute names are stable across its major versions. | The current version emits GenAI-convention span names, so anything keyed on the previous version's names finds nothing. Its legacy mode also reports time to first chunk in milliseconds where the current mode reports seconds. | A dashboard silently matches zero spans, or a latency chart is wrong by a factor of one thousand with no error anywhere. |
| `gen_ai.client.operation.time_to_first_chunk` is a span attribute in the specification. | The specification defines that exact name, in seconds, as a metric histogram. The span attribute for the identical measurement is `gen_ai.response.time_to_first_chunk`. The model SDK emits the metric name as a span attribute, so the name and unit are right and the signal is wrong ([GenAI metrics](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-metrics.md), [GenAI spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)). | A conformant query against the specification's span attribute returns nothing, and a metrics pipeline expecting a histogram receives none. |

Two of those rows deserve emphasis because they are indistinguishable from a code defect and they cost real time. Instrumentation that was never deployed reads exactly like instrumentation that does not work: the trace arrives, the call succeeded, and the new spans are simply absent. Instrumentation running in a process older than the fix reads the same way. Before forming any hypothesis about the tracing code, compare the running process or image against the commit that introduced the change.

One caveat on the whole specification column. The GenAI conventions moved out of the main semantic-conventions repository and now live in [their own repository](https://github.com/open-telemetry/semantic-conventions-genai), whose manifest declares `stability: development` and a `gen-ai-dev` schema URL, with no tagged release. Every `gen_ai.*` attribute, span, metric and event is badged Development; the only stable attributes on a GenAI span are borrowed from core conventions. The registry changed on the day it was read for this work. Nothing here should be treated as a stable target.

### 3.4 Does this belong upstream

Yes, and the argument does not require the maintainers to adopt an observability opinion.

Every span in this design is reconstructed from the outside, out of four callback entry instants plus the resolution of one streaming method. That reconstruction exists for one structural reason: the SDK dispatches consumer callbacks with no trace context attached. The shipped 2.2.0 bundle contains zero occurrences of `opentelemetry` in either its JavaScript or its type declarations, and its total self-reported timing surface is three items, none of which is a duration the SDK measured of itself. The interrupt callback in particular is dispatched straight from the WebSocket message handler, which is why a barge-in roots its own trace unless the consumer parents it explicitly by a span context captured earlier.

The smallest change that would remove the need for wrapping is a dependency on `@opentelemetry/api` alone, with one internal span per inbound prompt and per interrupt, and the corresponding callbacks dispatched inside that span's active context. The API package is designed for exactly this: with no SDK registered in the host application it returns non-recording spans, so a library can create them unconditionally at effectively no cost and with no opinion about exporters. Consumers would then get nesting instead of reconstruction, the interrupt callback would stop rooting its own trace, and per-turn boundaries would become observable without anyone reading the bundle to learn that prompts are serialised through a private promise chain. A slightly larger version of the same change would also close the playback gap by widening the inbound message union so that TwiML-subscribed playback and speaker events reach a handler instead of a dropped-frame debug log.

The honest counterweight is that the surface this design already leans on carries no stability guarantee. The callback types are exported and are not tagged internal, and the project's own conventions treat the internal tag as the marker for members consumers should not call, so not being tagged is a deliberate signal. Version discipline exists in practice; the DTMF addition reasons in semantic-versioning terms in its own release note. But no written policy backs any of it. Grepping the contributing guide, the readme and the development guide for stability, semantic versioning, breaking changes, public API or deprecation language turns up nothing on the subject, and no `@public`, `@stable` or `@experimental` tags are in use. The published API reference the readme points at returns 404 and serves an organisation-wide redirect stub, which is [an open issue](https://github.com/twilio/twilio-agent-connect-typescript/issues/93), so a reader cannot even check what the reference claims. Building on these hooks is a reasonable bet on intentionally exported surface, not an integration against a contract.

A reader weighing the maintenance signals should weigh these. The [repository](https://github.com/twilio/twilio-agent-connect-typescript) is public, MIT licensed and created in January 2026, with 14 stars and 9 forks at the time of reading. It reached 2.0.0 within about two months of 1.0.0 and 2.3.0 in its fifth month. Development is active but small and bursty: roughly twenty non-dependabot commits across two and a half months, clustered on release days, from effectively two maintainers plus one occasional contributor. Sixteen pull requests are open, about half from dependabot or Snyk. GitHub Discussions is disabled, there is no roadmap and no changelog, and only three issues have ever been filed, all of them documentation nits. That last figure matters for how you read silence: a search across issues and pull requests for OpenTelemetry, otel, tracing, metrics, spans and two tracing vendor names returns zero hits, but in a repository with a three-issue history, no issue about a topic is close to no signal at all. Absence of demand is not evidence of a decision against.

Two forward-looking signals cut in opposite directions. One open pull request adds vendor-facing product analytics that emit conversation and websocket lifecycle events to the vendor, with an opt-out environment variable; its emit functions are exported but tagged internal, which is an explicit statement that they are not a consumer extension point ([PR #95](https://github.com/twilio/twilio-agent-connect-typescript/pull/95)). It also refactors the messaging channel's send path into a template method, which is the one thing in it that would reach a subclass. Separately, a private staging repository whose public description says it holds a voice-provider foundation and a live-model port, and that it merges into the public TypeScript SDK, suggests the voice path is being reworked. That is precisely the path this tracing design wraps, and it makes the voice-specific parts of any wrapper the least safe thing to depend on. The version drift already observed is reassuring by comparison: the move from 2.2.0 to 2.3.0 was one additive pull request adding a DTMF callback, plus a behaviour-preserving extraction of the conversation-initialisation block, so a 2.2.0-shaped design still holds at 2.3.0.

### 3.5 The join to the companion page

The single most useful instrument in this entire design, the one that turns "is it us or is it the model" into one query rather than an investigation, is emitted by the model SDK running inside this process. A grep of the shipped Agent Connect bundle for `@opentelemetry`, `AsyncLocalStorage`, `trace.getTracer` and `traceparent` returns nothing, so every generation span and every `gen_ai.*` attribute on it, including the time-to-first-chunk value, comes from the model SDK's telemetry integration registered here at process start. Move the model call out into a separate agent runtime and that instrument leaves with it. Unless the replacement runtime accepts a W3C `traceparent` on its streaming request and continues the trace, one trace covering a whole call becomes two trees with no shared identifier, and the number both of these pages lean on is produced by a library that no longer runs where the spans are assembled. Whether any of the candidate agent builders propagates an inbound `traceparent` is an open question and is not settled anywhere in this work. The companion page in this pair, on replacing the agent core with a visual agent builder, is where that trade is argued; read this section first, because it is the cost side of that decision and it is easy to discover afterwards instead.
