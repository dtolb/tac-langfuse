# Page 2 draft: agent builder recommendation

## 0. Scope, and what this page does not repeat

The system architecture, the anatomy of a turn, the eighteen Agent Connect assumption/reality rows, the twelve OpenTelemetry ones, and the measured latency table already exist at https://pages-4296.twil.io/agent-scaffold-architecture (sections `#architecture`, `#turn`, `#tac`, `#otel`, `#numbers`, `#proven`, `#rules`, `#verification`). The argument about replacing the relay layer itself rather than the brain behind it is at `/convo-vs-livekit`, whose own footer records that roughly twenty-five of its claims, including every price, are sourced but unverified. This page assumes both and only asks one question: can a self-hostable open-source agent builder replace the hand-written TypeScript agent while staying behind ConversationRelay and the Agent Connect SDK.

Three constraints do the filtering. Requirement 1 is self-hostable open source in a local docker-compose stack with no hosted control plane and no paid gate on the feature we need. Requirement 2 is token-level streaming out of the runtime, because ConversationRelay synthesises speech from text arriving incrementally over a WebSocket and a runtime that returns one finished string per turn puts the whole generation time into the caller's ear. Requirement 3 is that tool definitions and their implementations are authored inside the builder rather than in our TypeScript source. Visual authoring quality and whether the builder also does prompt versioning and tracing well enough to retire Langfuse are scored, not filters.

## 2. The decisive fork, argued with numbers

Shape (a) is the builder's runtime imported as a Node library inside the existing process, so the `voiceChannel.on('prompt')` handler calls it directly and hands an `AsyncIterable<string>` to `sendStreamingResponse`. Shape (b) is the builder as a separate container reached over HTTP with a streaming body, with a generator in our process that reads frames and yields text deltas.

The Agent Connect seam is indifferent between them. `sendStreamingResponse` is a public method whose only contract is an `AsyncIterable<string>`, and it does one `ws.send` per chunk synchronously inside the `for await` loop (`dist/index.js:5277-5315`). `onMessageReady` is not the streaming path; it is the non-streaming auto-send convenience. So shape (b) needs no new abstraction, only a reader and an abort forward.

What shape (b) costs per turn is one request across a Docker bridge with a small JSON body, plus whatever the builder does before its first model token. The first term is a few milliseconds on a local bridge with TLS off, and I am marking the exact figure as an open item because nothing in this research measured it. Set against what we have actually measured, that term does not matter. The framework preamble in the current implementation is at most 84 ms, and that is a ceiling on one worst-case turn rather than a mean, with `prompt.fetch` at 41 ms running concurrently with `memory.recall` at 79 ms. A healthy tool-free turn is 586 ms to 801 ms of model time to first chunk. The cold first turn of a conversation, with a 2520-token input and no cache, was 3838 ms. A ten-millisecond transport hop is under two percent of the healthy figure and under a third of a percent of the cold one. ConversationRelay publishes no deadline for the first `text` frame after a `prompt`, no WebSocket idle timeout, and no time-to-first-token target, so nothing in the protocol envelope is violated either. The transport hop is not a problem and I am not going to manufacture one.

The term that does matter is the builder's own pre-model work, and it is undocumented for every candidate. Langflow builds or rehydrates a flow graph per run, Dify runs a workflow engine and, for the Agent node, an out-of-process plugin daemon and a separate agent-backend container, and Flowise builds the agentflow before the first LLM call. None of the four verdicts on streaming measured that interval. Our current 84 ms ceiling is the number a spike has to beat or accept, and it is the only honest way to compare.

One more envelope fact softens requirement 2 in a way worth stating rather than hiding. Voice Insights defines `tts_latency` as the time from receiving a text sentence to the start of audio synthesis, which is indirect evidence that Twilio buffers to sentence boundaries before synthesising. Twilio never states the aggregation rule, so this is inference. If it holds, a runtime that emits per-sentence rather than strictly per-token would be indistinguishable to a caller, and Rivet's 100 ms coalescing would probably not be audible. Rivet still fails requirement 2 as written, and it fails for a better reason anyway: the loop delta cursor is wrong on the second and later iterations of a tool loop, and text mode closes the stream at the first `nodeFinish`.

Where each survivor lands. Rivet and LangGraph JS are the only two candidates that can be shape (a); Rivet through `@ironclad/rivet-node` with `processor.on('partialOutput')` and no transport at all, LangGraph through `graph.stream`. Both fail a hard requirement for other reasons, Rivet on streaming through the loop and LangGraph on in-builder tool authoring. Every candidate that satisfies requirement 3 is a separate service, so the decision is made for us: shape (b), and the fork is not actually load-bearing. That is the useful finding, because it means the integration risk is not latency. It is two other things. The abort path has to reach upstream, so `data.abortSignal` from the `prompt` payload must be forwarded into the fetch, or a barge-in stops the local loop while the builder keeps generating and billing. And the transport must terminate in our process, because `handleWebSocketConnection` requires a live local socket in a private map and sessions are instance-local maps with no shared store, so the builder can be the brain but never the source of session truth.

## 3. The tools collision

Agent Connect ships `createMemoryTools`, `createKnowledgeSearchTool` and `createStudioHandoffTool`, and those are the reason Conversation Orchestrator memory, Twilio Knowledge retrieval and Studio handoff work. Requirement 3 says tool implementations belong in the builder. Those two facts collide, and one detail decides how.

Agent Connect never invokes a tool. `TACTool.implementation` is read in exactly two places in the whole bundle: the constructor, and the `execute` closure inside `toOpenAIAgentsSDKTool`. `toOpenAIFormat` and `toAnthropicFormat` emit schema only. The model runtime dispatches. So the moment the builder becomes the model runtime, the TAC tool objects are inert unless something re-exposes them.

Option one, re-expose the TAC tools to the builder over HTTP or MCP. We keep constructing the `TACTool` objects, wrap each `.implementation` in a route in our Node process, and register them in the builder as OpenAPI or MCP tools. Cost is five small shims, a schema kept in two places, and one extra local hop inside the tool cycle. That hop is noise against the measured tool costs of 417 ms to 1018 ms for `search_knowledge` and 266 ms for `handoff`, though `lookup_order` at 1 ms would become dominated by the hop. It preserves everything platform-side and it obeys the repo rule about working with Agent Connect rather than around it. It does not satisfy requirement 3 for those five tools: the definitions move to the builder, the implementations stay in TypeScript. This is the same limitation the Dify verdict found in Custom API tools and MCP tools generally, and the Flowise and Langflow MCP paths share it.

Option two, split by ownership. Platform tools stay behind option one's HTTP or MCP surface with implementations in TypeScript. Business tools, the `lookup_order` and `get_store_hours` shaped things a non-engineer would actually add, are authored end to end inside the builder, in Langflow's custom component editor, Flowise's Custom Tool, Sim's schema-plus-JavaScript pair, or Windmill's inline script. Cost is two authoring surfaces and an explanation of which is which. Note one thing that makes the split cheaper than it looks: memory injection does not depend on `createMemoryTools` at all, because `handlePromptMessage` awaits `retrieveMemoryIfEnabled` before our handler runs and voice uses `memoryMode: 'once'`, so the memory block arrives on the `prompt` payload as `userMemory` and can be passed to the builder as an input variable. Only knowledge search and Studio handoff need re-exposing.

Option three, give up the TAC-native tools. Knowledge search becomes a REST call to Twilio's Knowledge API authored as an HTTP tool in the builder, which genuinely does move the implementation into the builder. Studio handoff becomes a REST or TwiML action authored the same way, and the built-in tool's Studio path already returned 400 for an outbound call in the payment-reminder build, so there is a precedent for hand-rolling it. Cost is reimplementing two Twilio integrations, owning their failure modes, losing whatever Agent Connect fixes upstream, and breaking the standing instruction not to route around the SDK. It buys full compliance with requirement 3 and buys it at the price of the thing this scaffold exists to demonstrate.

Recommendation is option two. Platform tools re-exposed from our process as MCP, business tools authored fully in the builder. Say plainly on the page that requirement 3 is met for the tools a non-engineer would add and not met for the three platform ones, because the alternative is either a lie or reimplementing Twilio's own integrations to satisfy a rule.

## 4. The recommendation

Primary choice is Langflow. It is the only candidate that is unambiguously MIT with no carve-out anywhere near the path we use, ships no closed-source component in its compose stack, and has token streaming through a tool-calling loop confirmed in source rather than in documentation. `AgentComponent._get_llm` hardcodes `stream=True` and its docstring says the UI toggle is deliberately ignored because `astream_events` only emits `on_chat_model_stream` when the model is built streaming, and `process_agent_events` dispatches tool handlers and the token handler in the same `async for` iteration, which is precisely the property requirement 2 needs. Tool implementations really are authored in the browser, compiled and executed by `create_class`. Two things must be swallowed. The `/api/v1/run/{flow}?stream=true` surface is mislabelled: it sets `media_type="text/event-stream"` but emits bare newline-delimited JSON, so we split on blank lines ourselves and ignore the OpenAI-Responses endpoint entirely, which on `main` still drops the answer when no tokens stream. And browser-authored Python is unsandboxed in the server process with no way to sandbox it, which is acceptable at five users for a month on a stack that already publishes unauthenticated endpoints, and would not be acceptable otherwise.

Runner-up is Sim. Its wire shape is better than Langflow's for our purpose, because `stream:chunk` and `stream:tool` arrive on one stream, which would let the bridge reconstruct the tool spans the current trace already has rather than inferring them. Its custom-tool authoring is the cleanest of any candidate, a function-calling schema next to a JavaScript body with secrets bound out of source and masked before the result returns to the model. Its stack is far lighter than Dify's or Coze's. Sim wins if a spike shows two things: that `stream:chunk` really arrives per-token or per-short-fragment rather than per-sentence-buffer, and that the v1 SSE route rather than the v2 `application/x-ndjson` route is the stable target. If those hold, take Sim, because tool events on the same stream are worth more than Langflow's slightly cleaner licence.

Coze Studio is the strongest visual authoring experience and the only candidate that also answers the Langfuse question, through Coze Loop. It is not the pick because per-token deltas from the open-source backend were inferred from a frontend parser and a wiki page rather than observed, the Python code node has no identifiable sandbox service in the compose file, there is no DSL export so nothing is git-tracked, and the stack is eleven containers. Windmill is the sleeper and would be the pick on requirement 3 alone, but the single most load-bearing unknown in the whole sweep is whether its AI agent step exists in the Community Edition image or sits behind the `enterprise` compile flag. Settle that before spending a day on it.

What a spike has to prove, in the order that kills candidates fastest. First, that the builder's own pre-model latency is comparable to the current 84 ms preamble ceiling, measured as the interval from our HTTP request write to the first non-empty text delta arriving at the bridge, minus the model's own time to first chunk measured separately from the same host. Second, that inter-chunk arrival gaps at the bridge are small and even rather than sentence-shaped, reported as a distribution over roughly thirty turns rather than a mean. Third, that aborting the HTTP request on a real barge-in stops the builder's upstream generation, verified by the builder's own logs and not by the local loop exiting. Fourth, that a tool call in the middle of a turn does not suspend the text stream longer than the tool takes, which for `search_knowledge` means a silence of 417 ms to 1018 ms is expected and anything more is the builder's overhead. Fifth, that a tool authored entirely in the builder's editor can call our MCP surface and return a result the model uses.

The measurement that settles it is a percentile table of time to first text delta at the bridge, over roughly thirty turns, against the tool-free healthy baseline of 586 ms to 801 ms, taken in the same session as a direct model call from the same host so the comparison is not contaminated by an upstream slow window. That last clause is not pedantry. One four-turn call in this repo landed inside a measured two-hour patch where the model was two to five times slower than surrounding windows, produced 6047 ms to 7723 ms times to first token, and would have made any builder look catastrophic. Never baseline against it.

## 5. What nobody should adopt here

Four non-OSI or effectively-non-OSI licences fail requirement 1 outright. n8n moved to the Sustainable Use License in March 2022 and says itself that it is source-available rather than open source, with use restricted to internal business purposes, plus a separate `LICENSE_EE.md` for any path matching `.ee`. Arize Phoenix is Elastic License 2.0 for the server and for `arize-phoenix-evals`, with only `arize-phoenix-otel` under Apache 2.0, and third-party lists calling it Apache 2.0 are wrong. Open WebUI is BSD-3-Clause with a fourth branding clause added in 0.6.6, GitHub reports NOASSERTION, and the project concedes it is not OSI-approved. FastGPT and Typebot add their own terms, the former an Apache-plus-no-SaaS variant and the latter the Functional Source License. Activepieces is the textbook open-core failure: MIT core, commercial licence over `packages/ee`, and Agents and Chat explicitly excluded from the Community Edition, which is exactly the feature we would need. Botpress self-hosting is sunset, so the product is SaaS-only in practice. PromptLayer has no self-host at all.

A whole category gets mistaken for agent builders and fails requirement 3 by construction, because these tools observe or store prompts but do not orchestrate and do not execute tools: Agenta, Opik, Lunary, Helicone, PromptLayer, and Phoenix. Arize states the design principle in its own words, that it deliberately did not build prompt management because applications depending on an observability tool at runtime is an ill-advised design, and that the runtime handles execution while Phoenix handles observability. Pezzo is dead, with its last release in May 2024 and an archived examples repo. Latitude relicensed to MIT and pivoted to being an AI monitoring platform, so its current repo is trace search and PII redaction rather than an agent builder. Any of these could replace part of Langfuse. None replaces the agent.

Retired or dormant projects to leave alone: Microsoft Prompt Flow, whose feature development ended in April 2026 with runtime images already frozen including security updates, and whose successor is a code SDK rather than a builder; AutoGen Studio, since `microsoft/autogen` has been in maintenance mode since October 2025 and Studio's declarative-JSON model can only express serializable properties, so callables and hooks cannot be authored in the UI; Superagent, whose organisation pivoted entirely to AI security; Inferable, whose last commits across the control plane, app and CLI are February and March 2025 with sibling repos archived.

Wrong-shape candidates worth naming so nobody re-litigates them: Julep, which is otherwise a genuine contender with Apache 2.0, docker-compose and a real tool system, and whose own FAQ states that streaming is planned and not implemented, which is exactly the one-string-per-turn failure that puts full generation time in the caller's ear; Chainlit and CrewAI Studio, which are chat and Streamlit front ends over code you write; Kestra, whose execution model is task outputs rather than token deltas; RAGFlow, a strong retrieval product whose design centre is not tool authoring or streaming to an external relay; Vapi and Bland, neither of which is open source, with Bland's "fully self-hosted" marketing meaning Bland hosts its own model.

Two things sit adjacent and should be decided deliberately rather than dismissed. LangGraph Studio is not part of the MIT surface: it has no source repo and no npm package, `dev.mts` opens `https://smith.langchain.com/studio`, and the prerequisites are a LangSmith account and API key, with self-hosted LangSmith an Enterprise add-on requiring a purchased key and egress to `beacon.langchain.com`. And Pipecat, LiveKit Agents and Vocode are Apache or MIT and self-hostable, but they own speech-to-text, text-to-speech and interruption, so they replace ConversationRelay rather than sitting behind it. Pipecat Flows is the only genuinely visual voice-agent authoring tool in open source, which makes it worth a deliberate decision. That decision is already argued at `/convo-vs-livekit`, including the point that LiveKit's own telephony quickstart tells you to connect a Twilio Elastic SIP trunk, and the counted cost of moving from four vendor-run conversation services to nine customer-operated subsystems.

## 6. Honest limits and open items

Documentation rather than measurement, in this output. Windmill's token-delta streaming over webhook SSE endpoints was read from Windmill's own docs, not from source or a running instance, and the event and payload shape is unknown. Whether Windmill's AI agent step exists in the Community Edition Docker image or only behind the `enterprise` compile flag is unresolved and is the single most load-bearing unknown for that candidate. Coze Studio's per-token deltas were inferred from `conversation.message.delta` in a frontend SSE parser plus wiki-documented Stream Run endpoints; no live call was placed against a self-hosted `coze-server`. Where Coze's Python code node executes, and whether it is isolated at all, is unknown, which matters because this stack publishes on a public host. Whether Coze's code node supports JavaScript in the open-source build is unknown; only Python is named in the repo README. Whether Coze Loop's Apache 2.0 licence is as clean as Coze Studio's was reported second-hand. Numbers that carry mandatory caveats. The 84 ms framework overhead is a ceiling on one worst-case turn attributed to plus or minus one millisecond, with a range of 0 ms to 84 ms across every turn measured, and it supersedes an earlier 46 ms preamble figure that measured something slightly different. The 586 ms to 801 ms tool-free baseline and the 1282 ms to 1433 ms tool-turn figures come from a handful of turns on one day with one caller and one model, and are not a benchmark. The 3838 ms cold first chunk is a single cold-cache, two-generation, tool-calling turn, and span durations do not sum to that turn because the tool fires as soon as arguments parse and overlaps the first generation. The 33-generation sample behind the conclusion that `gen_ai.client.operation.time_to_first_chunk` accounts for the generation span almost exactly is one day, one caller, one model. The claim that the memory block is 52 percent of the system prompt uses base plus memory as the denominator; including the 4035 characters of tool definitions gives 35 percent, and the two figures disagree because the denominators differ. Prompt-share percentages are characters divided by four, and the tokenizer reported 2520 input tokens where that method predicts about 3132, an overestimate of roughly 24 percent, so trust the shares and not the absolute counts. The 6047 ms to 7723 ms times to first token from the 17:56 UTC close-out call landed in a measured two-hour upstream slow patch and must never be quoted as a latency baseline, though the tool-free 3835 ms SMS turn from the same window is quotable as evidence that the slowdown was upstream rather than structural.

Questions this research could not settle, which belong in the open-items section verbatim. The transport cost of shape (b) across a Docker bridge was never measured; every statement above that it is small relative to model time rests on the measured model figures plus an unmeasured assumption that a small-body local HTTP request costs single-digit milliseconds. No candidate's internal pre-model latency was measured, so no candidate can be compared against the 84 ms preamble yet. Whether ConversationRelay buffers text to sentence boundaries before synthesis is inference from the Voice Insights definition of `tts_latency` and is never stated as a protocol rule, so the conclusion that per-sentence chunking would be inaudible is unproven. ConversationRelay publishes no WebSocket idle timeout, no deadline for the first `text` frame after a `prompt`, no time-to-first-token target, and no numeric value behind its max-call-duration or concurrency errors, and absence of documentation is not proof of absence. Whether Twilio discards queued-but-unspoken tokens on `interrupt` is not stated anywhere in the reference. The end-to-end viability of feeding `sendStreamingResponse` from a remote runtime is derived from reading the shipped Agent Connect code, not from running it: abort propagation into a remote fetch and the `promptQueues` turn-boundary behaviour under a remote round trip were both unexercised. The live barge-in path for the current tiled-span instrumentation is unverified, since both real calls recorded `turns.aborted=0`. Langfuse v4 in `events_only` mode has no public read API, so trace verification is a UI or ClickHouse check and never an API assertion, and a 404 there means disabled rather than empty. Finally, the `/convo-vs-livekit` conclusions cited above carry that page's own disclaimer that roughly twenty-five claims including every price are sourced but unverified as of July 2026; the architectural conclusions are safe to cite and every number on it needs rechecking.
