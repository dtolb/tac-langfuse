# What happens to the trace when the model call leaves this process

## The premise, checked rather than assumed

The Agent Connect SDK carries no tracing of its own. Grepping the shipped `twilio-agent-connect` 2.2.0 bundle (both `dist/index.js` and `dist/index.d.ts`) for `opentelemetry`, `AsyncLocalStorage`, `traceparent`, `trace.getTracer`, `W3C` and `propagation` returns zero matches for every one of those six strings. Every generation span in a trace today therefore comes from the model SDK running in this process, and the attribute the latency argument rests on, `gen_ai.client.operation.time_to_first_chunk`, is a literal string inside the installed `ai` package at version 7.0.93. It is not in the Agent Connect bundle, and it is not in anything Twilio ships. Move the model call into a separate runtime and that instrument leaves with it.

One further detail decides how portable the attribute is. The OpenTelemetry GenAI conventions define `gen_ai.client.operation.time_to_first_chunk` as a histogram metric, and the span attribute for the same measurement is `gen_ai.response.time_to_first_chunk`. The AI SDK emits the metric name as a span attribute, which is the one thing the spec does not do with it. So a builder that is spec clean and does emit time to first chunk will emit it under a different key, and any query written against the current spelling reads nothing even in the good case.

## 2. What a reader actually loses when the answer is no

The loss is not abstract. Today a voice call produces one trace whose root is fully tiled by alternating spans covering the caller side and the bot side, with the generation subtree hanging under the turn. After a migration with no propagation, that root and its tiling survive, because our handler still sees the prompt frame and the first and last token on the socket. What lands in a second, unrelated trace id is everything the model runtime knows. Nothing joins the two except a correlation attribute we would have to invent and stamp on both sides, and the GenAI conventions offer only a flat one, `gen_ai.conversation.id`, with no conversation span and no cross turn parent and child convention. Two trees, one call, and a reader who wants the model detail for a turn has to search a second system by hand.

Named specifically, the attributes that stop existing here are the ones no bridge can recover: input and output token counts, cache read and cache write tokens, the model identity per step, the prompt and completion text, and the request issuance instant that makes time to first chunk meaningful. The prompt version link goes too, and for a reason particular to this stack: Langfuse computes the prompt name and version only for observations typed as generations, so a span our bridge synthesises and types as a plain span carries the attribute and still resolves to nothing. That behaviour was verified in this repo by reading the ingested rows directly, because this deployment mode exposes no public read API for traces, so a 404 there means disabled rather than empty.

What a reader uses instead is the number this repo already measures by hand: time to first token, anchored on the first non empty text delta rather than on the SDK's first chunk, because a turn that opens with a tool call streams tool argument chunks with no audible output for hundreds of milliseconds. That measurement survives the migration intact, because the bridge still reads the stream. It answers "how long until the caller hears something" and it does not answer "was that the model or was that us", which is precisely the question the vanished attribute answered in one query.

Can a bridge in our process reconstruct the missing spans from the builder's stream events? Partly, and the honest split matters. Wall clock shape is recoverable: first token, last token, and, if the builder streams tool lifecycle events, the tool call boundaries. Round one established that some builders do not even give you that much, since a candidate that coalesces deltas on a timer or emits the whole answer as one chunk erases the shape you were trying to reconstruct. Nothing that only the model client observes is recoverable at any fidelity, and a synthesised generation span is a record of our observation of a stream rather than of the model call: it starts at the first byte we read, so it already includes the transport hop and the builder's own preamble, and reporting time to first chunk from it double counts both. There is also a local trap. In this repo the span processor filters on export by instrumentation scope and by the presence of any attribute key beginning `gen_ai.`, so a span created with a bare tracer is created successfully, is visible to an in memory exporter, and is silently dropped on the way out. A synthesised generation span has to come from the sanctioned factory or carry GenAI attributes, or it disappears with no error anywhere.

## 3. Stitching patterns, ranked by how much they preserve

Propagating a `traceparent` and letting the builder continue the trace preserves the most. The cost is one inject call at the streaming request, a builder that is instrumented, and a builder configured to export where we already export. This repo makes the first part nearly free, because it already serialises a W3C traceparent per conversation instead of holding an async context open across minutes of WebSocket frames, so the header exists before anyone asks for it. Two conditions decide whether it works. The builder's sampler has to respect the parent decision, which Dify's `ParentBasedTraceIdRatio` does by construction. And the builder has to record the spans you came for, which is where Langflow fails despite passing the header test. One caution belongs with this pattern: an inbound trace header is caller controlled, and LangSmith's own documentation says to strip such headers at the gateway for public or untrusted traffic, since a caller could otherwise shape how runs are recorded.

Running the builder's own collector and forwarding to one backend preserves less than the name suggests. It solves "one place to look" and it does not solve "one trace"; without the header the trace ids still differ and you have two trees in one backend rather than two trees in two backends. Its real uses are narrower and worth keeping in view: translating a proprietary export format, and filtering attributes before they reach a backend that bills per span. The cost is a process to run and a configuration to maintain, and it composes with the first pattern rather than substituting for it.

Having our bridge synthesise child spans from streamed events preserves the least and costs the least. All the code is ours, the builder changes not at all, and the result is a trace that looks complete and is not: correct wall clock boundaries, no token accounting, no cache visibility, no prompt or completion text, no honest time to first chunk, and a shape that silently degrades to a single flat span against any builder that coalesces its deltas. It is the right pattern for exactly one situation, which is a builder that will never emit spans we can reach, and it should be labelled as a reconstruction wherever it is presented rather than drawn as though a model span were measured.

For the in process candidates none of these three is needed, and that is the strongest position available. A library called inside the existing turn span inherits the parent from the ambient context, and its spans reach the same exporter, so the trace was never broken and there is nothing to stitch.

## 4. The specific warning: Langflow drops the spans this scaffold exists to show

Langflow's own source says what it does, at length, and it is a deliberate design rather than a gap. Its application tracer is named `langflow.observability`, chosen so as not to collide with the LLM tracer integrations, and the module explains that spans, metrics and logs "all three deny by default on the way out". The span export allowlist contains four entries: the ASGI scope, the FastAPI scope, the SQLAlchemy scope, and Langflow's own application tracer. The comment above it states the reason without hedging, that the LLM instrumentors ship inside the same `opentelemetry.instrumentation.*` namespace as the application ones and "their spans carry prompt and completion text, which must never reach the operator's APM, so anything not named here is dropped". The allowlist is also not wideable by configuration: `exported_span_scopes` documents that it "only ever subtracts" and that a setting able to add a scope "would be an env var that reopens the leak the allowlist exists to close". The volume comment quantifies what does come out, roughly eighty percent of exported spans being database spans and about fifty spans per flow run "against one `flow.execute`".

Stated in the terms the situation deserves: adopting Langflow as the model runtime for a scaffold whose purpose is per turn tracing means the per turn generation spans cannot be reconstructed from either side. Not from Langflow, which drops them at export by design and forbids widening the filter. Not from our bridge, which never sees the model call and cannot invent token counts, cache behaviour or the model's own first chunk instant. What arrives in the joined trace is one `flow.execute` span with flow inputs and outputs, wrapped in HTTP and database spans. For a demonstration of tracing that is close to disqualifying, and it should be weighed as such rather than filed as a limitation.

There is a partial escape and it is worth naming precisely so nobody overrates it. Langflow separately ships LLM tracer integrations, Langfuse among them, which do carry prompts and completions and send them through their own clients. So the generation payloads exist and can reach the same vendor, keyed by Langflow's own identifiers, as a second tree rather than as children of our turn span. Whether that integration will nest under an inbound trace context is unverified; the repository's tracing tests in this area cover instrumenting outbound HTTP clients, not inbound parenting of the LLM tracer.

## 5. The measurement that settles it, in one spike

Stand one candidate up next to the existing agent and place one real call. Inject the active context into headers with the standard W3C propagator at the point where the turn span is created, send the turn to the builder's streaming endpoint with that header, and point the builder's OTLP exporter at the same destination the agent already uses. Then answer five questions, each of which is a single query rather than an investigation.

- Count the distinct trace ids belonging to the call. One means the header worked. Two means it did not, whatever the documentation says.
- Check that the parent span id of the builder's topmost span equals the span id of our turn span. A shared trace id with a missing parent is a link, not a nesting, and it renders as a separate root.
- Search every span in the tree for a time to first chunk attribute under both spellings, the metric style name the AI SDK emits and the span style name the conventions define, and for any token usage attribute at all. This is the question the migration turns on, and a null answer here is the finding.
- Subtract the builder's earliest span start from our own first non empty delta timestamp. That difference is the transport hop plus the builder's preamble, measured rather than argued.
- Compare cached input token counts on the first turn against a later turn in the same conversation. This catches the failure a header cannot fix: a builder that rebuilds the system prompt per run, reorders tool definitions or injects a run identifier into the prefix turns every turn into a cache miss.

Two figures to compare against, each with its caveat attached here rather than in a footnote. A healthy tool free turn on this stack measured between 586 ms and 801 ms of model time to first chunk, across a handful of turns on a single day with one caller and one model, so treat it as orientation and not as a benchmark. The framework preamble around the model call measured 84 ms, and that is a ceiling taken from the worst turn observed across thirty three generations on that same day, not a mean; the range across turns started at zero. Do not baseline against the one call that landed inside a measured two hour upstream slow window, where time to first token ran several times worse than every surrounding measurement and where a tool free turn took multiple seconds; those numbers describe the upstream provider that afternoon and nothing about this architecture.

If the spike returns one trace id, a real parent link, and any token usage on the builder's spans, the migration keeps the observability story. If it returns two trace ids, the honest description of the result is that the scaffold traces its own relay layer and correlates by hand to a second system for the model, which is a different and smaller claim than the one it makes today.
