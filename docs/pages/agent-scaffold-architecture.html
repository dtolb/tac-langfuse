ConversationRelay · Conversation Orchestrator · OpenTelemetry

One agent, three channels, every turn traced

A reference scaffold for customer-facing voice and SMS AI demos. A phone call, a text message and a browser all reach one turn function. Prompts, the model and the tool list are versioned outside the code, and each turn lands in a trace you can argue with.

Everything below was measured on real traffic rather than reasoned about. Where a number carries a caveat, the caveat is next to it.

02 Anatomy of a turn · select any hop

One voice turn, in the order the spans appear. A text turn is the same ladder without hops 01, 02, 09 and 10: the message arrives on a webhook and the reply is one complete answer rather than a stream.

A · The turn itself

caller.turn spans the gap

Streaming recognition decides the caller has stopped and emits a final transcript.

This is inside caller.turn, the span that covers every instant between two agent turns. It is a blend of bot playback, caller speech and endpointing, and it was 65 percent of one real call. Do not read it as how long the caller talked.

The transcript arrives as a prompt message. The timestamp is captured as the first statement of the handler, and the turn span is back-dated to it.

The turn span opens here and caller.turn closes here, which is why the two tile with a measured 0 ms between them. Everything before this point, socket frame parsing and queue serialisation, is not measurable from inside the app.

The adapter calls the turn function and gets back a token stream plus a promise that settles when the turn is done.

The adapter owns the span, not the core. A span created inside the core would close before the model streamed a token and every model span would land in a different trace. The token stream also has to be consumed before the caller's next await, or the first-token timing comes back null while the caller still hears the whole answer.

The prompt version, its model and its tool list are fetched from the prompt store while the caller's memory profile is recalled from the platform.

Measured at 41 ms for the prompt fetch running alongside 79 ms for the recall, which is the whole framework cost of 84 ms per turn. Everything else in a slow turn is model time. If the prompt store is unreachable the compiled-in default answers and reports its version as fallback, so a degraded demo is visible rather than silently different.

One streamed model call with the resolved tool definitions attached.

The AI SDK writes gen_ai.client.operation.time_to_first_chunk natively on every generation, in seconds, and across 33 generations it accounted for the generation span almost exactly. That turns "is it us or the model" into one query. A cold first turn measured 3838 ms here against 0.51 to 0.71 s once the prompt cache was warm.

The model asks for a tool, the tool executes, and the result goes back as another step.

Measured: a local lookup at 1 ms, a knowledge search at 417 to 1018 ms, a handoff at 266 ms. The caller hears silence for that whole time, which is the argument for a filler line rather than for a faster tool. Tools that need live credentials are built lazily inside execute, so a missing credential is a structured miss the model can talk about instead of a crash at boot.

With the tool result in context, the model produces the words the caller will hear.

This is why a tool turn's time to first token structurally contains the whole tool cycle. Tool-free turns measured 586 to 801 ms on a healthy model against 1282 to 1433 ms for tool turns, so comparing the two as if they were the same thing invents a regression.

The turn function yields tokens as they arrive; the adapter forwards each one immediately.

The turn records a first-audio proxy at the first non-empty token. It landed within 0 to 3 ms of first-token on all six turns of a call, which is a useful negative: it proves nothing queues between the model and the socket. It is not time to first audio, and presenting it that way would be wrong.

Tokens go out on the socket as they arrive, then an end-of-turn marker closes the turn.

The end marker is only emitted if at least one token was sent, so an empty answer closes nothing and the caller holds an open line forever. That one has bitten: an empty answer must speak a fallback. Guarding on "we accumulated some text" is also wrong, because text accumulates before the send.

The platform speaks the tokens, and the next caller.turn is already running.

First byte of audio and end of playback are not exposed, so this is the part of the call the traces cannot see. It shows up as the tail of the root span, 2394 ms on the instrumented call, and as the bulk of every caller.turn. Getting the real number means Voice Insights or media stream marks.

A barge-in stops playback and delivers an interrupt, then the caller's words arrive as the next prompt.

Three things are load-bearing here. The abort signal must be passed explicitly into the send, or the fallback resolves to undefined and the caller is talked over with the answer they just interrupted. The interrupt handler parks the boundary instant rather than ending the span, because the turn's output and tool list are written after the stream settles and would be dropped on an already-ended span. And a pending hangup has to be cancelled, or the call ends on someone a turn later.

Barge-in history keeps the generated partial, which overstates what the caller actually heard. The ground truth arrives after history is appended and is deliberately not written back.

B · After the last turn

The half that is easy to get wrong, because most of it happens after anyone is listening.

The caller hangs up, or the agent decides to. An agent hangup is a two-step mechanism: the tool records an intent, and the frame goes out after the farewell has streamed.

Tools run inside the model loop, before the turn's text exists, so hanging up in the tool would cut off the goodbye. Queued audio does drain before the socket closes, measured at 1.75 s on a real call, which the docs do not promise. A handoff beats a pending hangup unconditionally, because two end frames on one socket is undefined behaviour.

The root span takes its metadata from a stats call that finalises the call first and reports second: turn count, aborted count, total caller time, first-audio median and maximum, and why the call closed.

There is deliberately no accessor to call in the wrong order, because root metadata computed from a half-open call would be quietly wrong rather than obviously wrong.

On shutdown the conversation is closed first, then telemetry is flushed.

That order is not cosmetic. An unended span never arrives, so flushing first ships every turn while dropping the conversation they hang from. The flush itself has to go through the provider's delegate, because the proxy the API hands you has no flush method and calling it optionally is a silent no-op.

When the conversation closes, extraction writes observations to the caller's profile, which the next conversation recalls.

Measured about 2 seconds from closed to the observation existing. The slow part is the close itself, which took 5 minutes 36 seconds on an ordinary conversation and 32 seconds after a handoff, because the handoff writes an inactive state that short-circuits the wait. Extraction also survives a handoff, which is the opposite of what was expected.

The lever that is actually top of the list

On a cold turn the system prompt divides roughly into the base prompt at 33 percent, the injected memory block at 35 percent, and five tool definitions at 32 percent. Those are character shares rather than token counts: the tokenizer reported 2520 input tokens where characters divided by four predicts about 3132, so trust the shares and not the absolutes.

The memory block is the part that moves. Across one day, same caller, it went 2341, then 1837, then 3303, then 4412 characters, a net 88 percent growth, and it is not monotonic, so the platform rewrites rather than only appends. Nothing in the composition path caps it. The prompt cache absorbs it from turn 2 onward, which means it is paid precisely on the turn that is judged.

Tool descriptions are the next largest block and they are not free to trim: the knowledge search description is 1244 characters and is load-bearing, because relevance scores are normalised per query and cannot gate on their own.

Two queries that settle an argument

The resource attribute host.name is a container hash for a containerised run and the machine hostname for a host run, which is the fastest way to tell which process produced a trace, and how container cold start was ruled out as a cause.

The memory block size is readable per conversation as a character count on the recall observation, with no code change required.

04 Working with the Agent Connect library · assumption against reality

The framework that boots both channels, owns the WebSocket, and provides the memory, knowledge and handoff tools. Everything below was found by reading its source or by watching it run at version 2.2.0, and the right instinct throughout was to extend it rather than work around it. Its 31 test files are usable as evidence, which is worth knowing because it is easy to assume a vendor bundle ships none.

A · Boot and wiring

The assumptionWhat is actually trueSymptom when you get it wrong
Registration order is cosmetic The server constructor snapshots channels, and the inbound webhook route is only registered if a webhook channel already exists. A 404 on the webhook with one log line about no channels configured.
Construction is local work Creating the client makes a network call to read the orchestrator configuration, and it rethrows. Boot fails for reasons outside the process, so config resolution has to tolerate it.
Optional config keys can be omitted Several path options wrap a default in a preprocess step, so the key is required even though a value is not. Pass explicit undefined. A schema error at construction, from a key you deliberately left out.
The library reads the environment for you It can, and taking that path makes it a second place the environment is read. Two sources of truth for configuration, and a boot that cannot degrade politely.
Inbound SMS arrives on the number's webhook It arrives through the orchestrator configuration's status callback plus bidirectional capture rules, in an event envelope rather than a form post. A 200 response, an unhandled-event log line, and total silence.
The server can own the listen call Its start method calls listen itself, which forces two mutually exclusive boot paths where only one of them listens. Either a double listen or a process that never binds, depending on which path you took.

B · What it does not do, so you must

The assumptionWhat is actually trueSymptom when you get it wrong
It composes the prompt from memory for you Its prompt builder has zero callers inside the library. What reaches the model is entirely the host's decision. You believe a memory block is being injected when nothing is. This corrected an assumption that survived two whole tasks here.
Every channel hands you an abort signal Only the voice path does. A text turn has no timeout unless you synthesize one. An unbounded turn leaves its span unended, so the turn never reaches the trace at all.
There is an end-session method There is not. It builds the end frame for a handoff and parks it, and only drains it on the non-streaming send path. On a streaming channel the parked frame is never sent. The socket is public, so writing the documented frame yourself needs no internals.
Returning an empty reply is safe An empty string is a silent no-reply, and a thrown error inside the handler is caught and logged. Nothing is sent and nothing is raised. Four further conditions drop an inbound message the same way, all of them logging rather than raising.
The message-ready callback is per channel It is a single global slot on the client, not on the channel. The second channel silently replaces the first. Branch on the channel inside one handler.
Its callback route can double as your call-action URL That route answers plain text, never markup, and its payload schema has no field for handoff data, so a non-strict parse strips it. The callback keeps arriving and looks healthy while the handoff data is discarded and the call drops. This one refuted an earlier written conclusion that the two could coexist.

C · Memory, and the shape of the tools

The assumptionWhat is actually trueWhy it matters
Memory mode controls what the model sees It controls exactly one thing: whether recall runs, and how often. The response is handed to your callback and you decide what to do with it. Choosing a mode is a latency decision. Composing the block is a separate, host-owned decision.
A conversation can benefit from its own memory Extraction is post-conversation only. Memory makes the next conversation smart. A demo that texts once and expects recall will fail, correctly.
Recall failure is a no-op On failure it falls back to listing the current conversation's communications with no limit. The fallback can render the conversation into its own prompt, which is why the compose step here makes that section structurally unreachable rather than trusting a config value.
A tool in the catalog is a tool the model has A prompt has to name it. Typecheck, a full test suite, the boot log, the health route and a tool-resolution diagnostic all passed while two new tools were dead. Green checks do not prove a tool is offered. Only a real turn does.
Voice and digital handoff need separate tools There is one tool that branches on the session channel internally, and the two wire shapes are not interchangeable. Building two was a decision that had to be reversed after reading the source.
Default tool descriptions are fine The default handoff description invites a transfer whenever the model feels stuck. Overriding descriptions is behaviour work, not copy editing.

Shutdown is where three timeouts disagree

The library registers a graceful-shutdown plugin with no options, which means a 10 second watchdog, and separately waits up to 30 seconds for WebSockets to drain. The plugin runs every handler before closing the server, so a host flush registered there sits behind the 30 second wait while the watchdog exits at 10. The last turn is lost, silently.

Register the plugin yourself with a longer timeout before starting, put the drain in the pre-close hook rather than the close hook, since the close queue runs last and would deadlock against the connections it is waiting on, and do not add your own signal handler: the plugin installs one and warns about duplicates. Registering the plugin twice throws.

A · The export pipeline

The assumptionWhat is actually trueSymptom
Any OpenTelemetry span reaches the backend The span processor forwards only spans that pass its own filters for its span types. The span is created correctly, is visible to an in-memory exporter, has a real sampled trace id, and never arrives. This is the single most expensive finding on the page.
Custom attributes ride at the top level The attribute builder destructures a fixed key set. Anything custom has to nest under metadata, where the key is preserved verbatim. The attribute is simply absent, with no warning.
A flush on the global provider works The tracer provider you get back is a proxy with no flush method, so an optional call resolves to nothing. Flush through its delegate. Spans are lost at exit and the code reads as if it flushed.
Metadata values round-trip The serializer's guard is truthiness, so false and an empty array survive while null is dropped. A deliberately null field produces no attribute rather than an explicit null.
Flush, then shut down An unended span never arrives, so the conversation has to be closed before the flush. Flushing first ships every turn while dropping the conversation they hang from.
Missing spans mean broken instrumentation A container image copies the source at build time rather than mounting it. A real call against a stale image returns a trace with none of the new spans, which reads as "the instrumentation does not work" instead of "the code was never deployed".

B · Linking and nesting

The assumptionWhat is actually trueSymptom
Wrapping the model call in your own span parents it Starting an observation does not make it the active context, so the SDK's spans parent to the turn span instead. Your span is a timer running alongside, which is why its duration and the model span's are near identical rather than nested. An earlier version of our own diagram drew this wrongly, and reading the parent id settled it.
The prompt link goes in telemetry metadata That field does not exist on the current SDK. The link rides on runtime context, must be opted into, and must be a plain object with a string name and a numeric version. A stringified version is discarded with no warning and the metrics view stays empty.
Any span can carry the prompt version Ingestion computes the prompt link only for generation observations. Per-version latency aggregation works at the model-call level with a native time-to-first-token column, while turn-level timings are filterable but not aggregated.
Span names start with the SDK's own prefix They follow the OpenTelemetry generative-AI convention. Anything keyed on the old prefix matches nothing.
An in-memory exporter proves the pipeline It cannot exercise the real processor's filters, and a bare provider makes context propagation a no-op. The first harness run reported six trace ids for one call. It needs an async context manager and a propagator, and the live stack is still the only real proof.
A 404 from the read API means no data In events-only mode the trace read API is disabled and answers 404 by design. You go chasing a telemetry bug that does not exist. Verify in the UI, or read the event tables directly.

Say this accurately: the traces contain personal data

The app's own spans and events pass through a scrubbing hook. The model's spans do not: they carry the full prompt and the full completion, which on these channels includes whatever the caller said and whatever memory was injected. The memory store holds personal data too, since profile traits include a phone number and observations are prose taken from the transcript.

So this stack must not be described as keeping personal data out of the observability layer. What is true is narrower: log lines and the app's own event payloads are scrubbed, and the tool layer projects communications down and drops recipients, with a test asserting it.

06 What is proven, and what is not

Proven on real traffic

measured, not inferred
  • Both channels answered live, by the same turn function.
  • Memory across separate conversations, with the recall arriving on the next conversation and no tool call.
  • Barge-in on real audio, twice in one call.
  • A knowledge search answering a policy question on both channels.
  • An agent-initiated hangup, with the goodbye audible before the socket closed.
  • A caller transferred to a browser softphone that a human answered, carrying the reason and the transcript.
  • A held event stream surviving 184.7 seconds behind a proxy, ending only when the process stopped.
  • A clean shutdown that force-closed that connection and exited zero in under a second.

Each verified by executing it

Not exercised yet

honest gaps
  • The barge-in telemetry path. The interrupt attributes are proven by tests and a diagnostic; both instrumented calls report zero aborted turns.
  • The long shutdown drain. It needs a termination signal mid-call, which has not happened.
  • A signature rejection on the media socket, which is invisible by construction.
  • First byte of audio and end of playback, which the platform does not expose.
  • Reasoning-effort tuning. Model parameters were empty on all 33 generations, and no reasoning-token attribute exists on the span, so this is a hypothesis rather than a measurement.

Named rather than quietly omitted

Debt taken on purpose

a demo scaffold, not a service
  • Four unauthenticated endpoints on a stable public host: one mints a real voice access token, one spends the model key unmetered, one fabricates observability events, and one lists the names of unset variables.
  • Conversation state is process local, so a restart drops every conversation mid-call and two instances would not share them.
  • Basic auth is not the bolt-on it looks like: browsers only show the dialog for top-level navigations, fetch gets a bare 401, and an event stream cannot send the header at all.
  • The mitigation is operational. The stack does not restart itself after a reboot, so bringing the public surface up is always an explicit act.

07 Rules worth carrying to the next build

RuleWhat it cost to learn
Degrade loudly at boot, never refuse to start An empty configuration still boots here. Each missing variable logs what it costs, a health route reports a capability map, and only the routes that genuinely cannot work refuse. A demo that will not start is undebuggable at the worst possible moment.
A green check is not a proof Typecheck, a full suite, the boot log, a health route and a tool-resolution diagnostic all passed while two tools were dead. Only a real turn caught it.
Instrument the gaps, not just the work Before tiling the timeline, a 57 second call showed 12 seconds of spans and 45 seconds of unexplained gap. Covering the gap with its own span turned "where did the time go" into a reading rather than an investigation.
Find the native attribute before theorising The one attribute that answers "us or the model" was already on every generation and nothing here had read it. The whole latency investigation became one query.
Enforce architectural boundaries with tests The rules that matter here all fail silently: a vendor import in the wrong folder, a console call bypassing the scrubber, an undocumented environment variable. Each is a test, and some tests assert the rule sets themselves are intact.
Restart or rebuild before concluding a fix failed A verified-correct cache appeared to do nothing because the process predated the commit by 53 minutes. Separately, a real call ran against a container image built hours earlier. Both read as broken code.
Keep the vendor library in one folder One folder imports the platform SDK and the agent framework. That is what lets a browser drive the whole agent with no credentials, which is a runtime proof rather than a claim.
A claim inherited from an approved plan is still a claim Approval means the approach is agreed, not that every factual assertion in it was checked. The written record for this build corrects itself in more than twenty places, and several of those corrections were confidently worded first time around.

Two test-method traps that produce clean, wrong numbers

Texting the agent from a second number on the same account doubles every reply. Both message legs share the same pair of endpoints, so the capture rule matches each one, and the mechanism is two creation events about 300 ms apart. Measured against an external handset it is exactly one reply per inbound. Any "reply count" from an on-account number is inflated.

Knowledge search scores are normalised per query. An out-of-scope question scored 0.816 while the in-scope question's own second hit scored 0.54, so no threshold can separate them and the tool description has to carry the scoping.
